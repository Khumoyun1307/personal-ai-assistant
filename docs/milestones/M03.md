| # | Decision | Why |
|---|---|---|
| D44 | **Normaliser v2 = ASCII canonical form** (owner, 2026-10-22; D41 in M02.md): NFKC + casefold; every apostrophe-like character (ʻ ʼ ‘ ’ ' \` ´ ʹ ʽ ′) folded, then dropped; oʻ/o'/ö/ō/ŏ/ó → o; gʻ/ğ/ǵ → g; ş → sh, ç → ch, ñ → ng; Cyrillic → Latin with the Uzbek table (ў→o, ғ→g, қ→q, ҳ→h, х→x, ш→sh, ч→ch, ё→yo, ю→yu, я→ya, ц→ts, е→ye word-initially or after a vowel/ъ/ь else e, ъ/ь dropped) plus the Russian letters (щ→shch, ы→i, э→e, й→y); whitespace collapsed. `NORMALIZER_VERSION = 2`; `reindex-search` re-keys all retained rows and records the global `system_state.normalizer_version`. The spike prototype (`spikes/search/normalize_proto.py`) was ported, never imported. | People type Uzbek without the new alphabet or apostrophes; one key for 1995 Latin, new Latin, apostrophe-less Latin and Cyrillic. ARCHITECTURE §11.2. |
| D45 | **Taint** (owner clarification 2026-10-22; D42 in M02.md): the agent reads and works with everything; a run is tainted when its context includes third-party text — the current owner message with forwarded/quoted text, included history turns carrying such text or managed content, or tool results with contact-authored text. In a tainted run only model-initiated `configure`/`control` calls (other than `pause_autonomy`, `end_delegation`, cancel) become a one-tap confirmation card; reads are never blocked; the owner's direct commands and buttons need no card. `resume_autonomy` never runs from a model call. | Invariant 3b without blocking the agent's real work. ARCHITECTURE §7.1. |
| D46 | **Quoted text is stored** as `control_turns.quoted_text` (a new content column: registered in `privacy/content_columns.py`, ARCHITECTURE §10.1/§10.4, the deletion cascade and the retention sweep); forwarded text is the message text itself; `control_turns.third_party` marks either. | The agent must understand what the owner quoted; the column is covered like every other content column. |
| D47 | **Read tools** `search_messages`, `resolve_contact`, `get_conversation`, `list_conversations`: class `read`, run types {`owner_request`}, `min_tier = CONTROL_ONLY` (stored history stays readable while the connection is disabled), `returns_managed = True` (omitted without `ai_managed`), release flags `tool.<name>` default off. | ARCHITECTURE §8.2, §14.3; AGENTS §8. |
| D48 | **Per-route model configuration** `LLM_ROUTE_<RUN_TYPE>_MODEL` (default `LLM_DEFAULT_MODEL`). The processor of a route is derived from its model id in one table (`core/model_routes.py`: `gpt-*` OpenAI, `claude-*` Anthropic, `gemini-*` Google); the consent wrapper refuses an unknown model, a model of a processor the adapter does not serve, and a processor the consent does not name. | ARCHITECTURE §7.4; needed for the "route configured to a processor not named in the consent raises" test. Deriving the processor from the model keeps it to one setting per route, not two that could disagree. |
| D49 | **A forwarded control-chat message is never a command**, stop word or pending-input answer: it goes to the agent as a tainted turn. **Confirmed by the owner on 2026-10-23 by merging PR #10.** | Its text is someone else's; running a forwarded `/privacy revoke` would let a third party's text act as the owner (invariant 3b). The owner can still type the command. |
| D50 | **What counts as quoted third-party text:** a `quote` from another chat (`external_reply`) or from a forwarded message the owner replies to; an `external_reply` without a quote does **not** taint, because `ExternalReplyInfo` carries no text we store; a quote inside a forward belongs to the forward. **Confirmed by the owner on 2026-10-23 by merging PR #10.** | D45 taints on third-party text *in the context*; text we never store cannot be in it. Avoids wrapping the owner's own words as untrusted. |
| D51 | **`tool_confirmations.status` has two more values than planned** — `applied` and `failed` besides pending/confirmed/rejected/expired. | "Confirm applies once" needs a durable claim: the job moves `confirmed → applied` with a conditional UPDATE before running the handler (at most once, like every card), and a handler error ends as `failed`, never as done (invariant 11). |
| D53 | **Forwarded or quoted text from a managed chat is managed content** (review item O): the control inbox collects the origin (forward sender/chat, legacy `forward_*`, `external_reply` origin and chat, a forwarded message replied to); when it matches one of the account's contacts or conversations — or a hidden sender's name equals a contact's — the turn is stored `contains_managed`. Without `ai_managed` the model gets a "withheld" note instead of the text; managed-data deletion clears it. An unknown origin is not managed (nothing stored to match). **Confirmed by the owner on 2026-10-23 by merging PR #10.** | AGENTS §6 invariant 9: control turns that quote managed content need `ai_managed`. |
| D54 | **Query-side spelling alternatives** (review item K): each query term also matches zh↔j, kh↔x, x↔h, y↔i, k↔q, u↔o and initial e↔ye (one rule at a time, ≤ 24 alternatives per term). The stored key is unchanged, so write and query stay symmetric. | Russian typed in Latin (zhdu, ego, vy, khorosho) and Uzbek on a Russian keyboard (куп, raxmat) missed short words that trigrams cannot rescue. More recall, some extra noise; the S03.4 retrieval eval will tune it. |
| D55 | **Held-call hardening** (review items A, B, C, F, H): success is reported only for status `ok`; a handler exception ends `failed` with an "it may not have been applied" notice; a card shows the arguments in full (bidi and invisible characters made visible) or the call is refused; a repeated call reports the row's real state; the same pending change from a retried turn reuses its card; an ambiguous card send expires the card; `confirmed` rows whose job is lost are re-deferred by `system.reconcile_pending` and failed by the retention sweep after 24 h; the worker cannot be built without an applier. | Invariants 3b and 11. |
| D56 | **Taint decays** (lead decision on review round 2; **confirmed by the owner on 2026-10-23 by merging PR #10**): (a) every reply written by a tainted run (own or inherited taint) is shown to later runs wrapped as untrusted (`control_turns.from_tainted_run`, revision 0009); (b) only a reply whose run was tainted by its OWN inputs — the current turn's forwarded/quoted/managed text, or an untrusted tool result in that run — taints later runs (`third_party`); inherited-only taint does not propagate, and a reply's managed content read from history no longer counts either. | D55's "reply carries the taint" made taint permanent: every later configure call needed a card. With (b) the taint ends once its source leaves the 20-turn window; (a) keeps the model from treating a restated injection as the owner's words. |
| D52 | **Tool argument constraints are validated in Pydantic validators, not as JSON-schema keywords**; dates are `YYYY-MM-DD` strings in the owner's timezone (inclusive), not `format: date`. | OpenAI strict mode's support for `format`/length keywords was not verified against the official docs in this slice (no live call was allowed); plain strict schemas are known to work (S01.4). A unit test keeps those keywords out of every tool schema. |
| D60 | **Summary refresh cadence (S03.2):** a chat's rolling summary is refreshed once it has been quiet for 30 minutes (`SUMMARY_REFRESH_DEBOUNCE_MINUTES`), or at the latest 6 hours after its first unsummarized message (`SUMMARY_REFRESH_MAX_WAIT_HOURS`) — a trailing debounce: the job re-defers itself while messages keep coming. One incremental call per refresh (≤ 200 new messages per call, ≤ 5 calls). The reconciler re-creates a lost job one debounce out, so a chat whose refresh keeps failing is retried at most about twice an hour. **Pending owner confirmation.** | Summaries are long-term memory and get_conversation context, not alerts: freshness of minutes is not needed, and a quiet period groups a burst into one paid call. The catch-up does not depend on this cadence (it summarizes its period on demand). |
| D61 | **Background refresh is behind a release flag** `summary.refresh` (FEATURE_FLAGS), **default off**, like every tool. While off, content is still flagged (`pending_ai_since`), no job is queued, and the read tools summarize on demand. **Pending owner confirmation.** | It spends model budget without an owner request; the owner turns it on when ready (it is also what the S03.3 retention rollup will rely on). |
| D62 | **"Needs reply" check (attention list v1)** = the rolling summary's `needs_reply` and reason — no separate call type. When the attention list is asked, up to 8 chats whose summary is stale are refreshed inline with **one summary call each, never chained** (the same incremental call the background job would make, moved earlier); a chat with more unseen messages than one call reads (200), or whose refresh fails, shows `not_checked`, as do stale chats beyond the 8. Cost per ask: at most 8 summary calls, plus at most one retry of a truncated output each, plus — only when a chat changed during its call (owner addition to D63/D66) — one immediate repeat of that chat's call (itself with at most one truncation retry): 32 in the theoretical worst case, 8 normally, only for stale chats (review item 5). **Pending owner confirmation.** | No extra prompt or route to evaluate before S03.4; the verdict comes from the same summary the owner sees, and its cost is bounded. Triage (M05) upgrades it. |
| D63 | **A deleted message invalidates the summaries that covered it:** its chat's period caches are deleted, and the rolling summary if it covered the message; the rolling summary is rebuilt from the retained messages, and content that had already expired is recorded in `summary_gap_before` (answers then say earlier messages expired without a summary). **Owner addition (2026-10-25), also for D66:** when a summary is discarded because the chat changed during the model call (a deletion or edit), a background refresh says nothing and rebuilds at the next refresh (the flag stays set); an owner-requested path (`summarize_period`, the attention list's inline check) retries that chat once at once with the fresh messages, and if the retry is discarded too, returns the chat as NOT summarized (`changed_during_summary`) — never as an empty or complete summary (invariant 11) — with a notice written by our code ("…changed while it was being summarized (a message was deleted or edited), so it was left out. Ask again shortly…") that never quotes or describes the content; the other chats are unaffected, and `owner_request.v3` relays notices like caveats. **Pending owner confirmation.** | PRD §20 excludes keeping contacts' deleted messages; a summary that kept them would do exactly that. The cost is losing summarized context of expired messages in that chat. |
| D64 | **Catch-up = map per chat, deterministic combine:** one period summary per active chat (≤ 15 chats per catch-up, the newest ≤ 300 messages each, 4 calls in flight), cached as `kind = period` while the range's messages are unchanged (30-day retention); the combination (grouping needs-attention → commitments → other, the list of chats not summarized, coverage caveats) is done in code, and the owner model writes the reply. There is no model-written `CatchUp` and no separate reduce call. Caveats are the application's own English sentences; the prompt requires every one to be relayed. **Pending owner confirmation.** | One call per active chat keeps isolation (invariant 4) and cost linear; deterministic caveats cannot be dropped by a model before they reach the owner-facing model. The S03.4 evaluation measures whether the final replies keep them. |
| D66 | **An edit of a covered message is treated like a deletion (D63)** (review item 2, coordinator decision 2026-10-25): an edit that changes a message's content drops the chat's period caches and, if the rolling summary covered the message, the rolling summary too; it is rebuilt from the retained messages (with the new text). A message edited while a summary call reads it makes that summary discarded (the store re-checks content hashes). **Pending owner confirmation.** | The incremental refresh only reads messages after `covers_through_message_id`, so an edit was never reflected and the pre-edit text — which the contact chose to remove — stayed in memory. Cost: one rebuild per edit of an already-summarized message. |
| D67 | **`remember` stores the owner's words, not a paraphrase:** the model drops only the "remember that" framing and adds nothing (prompt rule, `owner_request.v4`); code trims and stores the text as given (1–400 characters, the confirmation card must show it whole). Kinds instruction / preference / fact / style; a note about one person is stored for that contact (the model resolves the contact first and asks when several match); anything else is the owner's own. A correction is `replaces_memory_id` (the old item is forgotten in the same change). No in-place edit. **Pending owner confirmation.** | Owner instructions are the owner's; a paraphrase could change what was meant and could not be checked. |
| D68 | **Echo with one-tap Undo for every executed configure call** (`remember`, `forget`, `set_conversation_mode`, `update_preferences`): the owner sees what changed with an Undo button; the button lives 24 h (the card lifetime), works once, and reverses the change only while the state it created is still in place (a later change is never overwritten — the owner is told "changed again since"; a preference change partly changed again is "partly undone" naming what stayed; a note already deleted is "no longer exists"). A confirmed change that was already so ("ignore" on an ignored chat) is reported "nothing to change", never "failed" or "done". The audit row of the change is the Undo reference (content-free: ids, enums, old/new setting values). Tool results tell the model whether the Undo button reached the owner. **Pending owner confirmation.** | PRD §11.2 / FR-MEM-01 ask for "explicit memory echoed back with a one-tap Undo"; ARCHITECTURE §8.2 asks the same for modes. One mechanism for all four. |
| D69 | **Forget = archive, then delete after the Undo window:** a forgotten item is never used again at once, stays restorable for 24 h (the Undo window), then the hourly retention sweep deletes it. Managed-data deletion and a bot-chat purge delete at once. **Pending owner confirmation.** | Undo of a forget needs the item; keeping it 24 h is the shortest window that matches the Undo card. |
| D70 | **Memory from other people's text** (revised 2026-10-26 by the safety review; the first version — such items preloaded wrapped and never tainting — contradicted invariants 3b and 9 and is withdrawn). An item saved by a run that had other people's text anywhere in its context — taint, a held call the owner confirmed, a tainted-run reply or a managed turn in its history window, or a run row that is gone (fail closed) — is stored `tainted` and, by the conservative rule, `managed`, with the ids of the chats/contacts its run drew on. Its text is never preloaded into a run: owner runs get a placeholder pointing at `list_memories` (and nothing at all without `ai_managed`); a `list_memories` result holding one is wrapped as untrusted, **taints the run** (a later change needs a card, 3b) and is marked managed for the consent wrapper (9); without `ai_managed` it is withheld and counted. Restating it cannot launder it (the restating run's context carries the tainted reply). The owner's own items (from untainted runs) are preloaded verbatim (≤ 30, newest first) as an input item with provenance; notes about contacts come only through `list_memories`. **Pending owner confirmation of the trade-off:** a run that read such an item needs a card for any later change in that run, and a note saved within 20 turns of a tainted reply is itself treated as from other people's text. | Invariant 3b: other people's text must not reach a run without tainting it, and nothing derived from it may pass as the owner's words. Invariant 9: an item that may hold managed-chat content needs `ai_managed` and goes with managed-data deletion. |
| D71 | **Managed-data deletion also deletes notes about the people in those chats** (contact- and conversation-scoped memory items) **and every managed-origin item in any scope** (safety review V2); the owner's own instructions, preferences and facts stay. A recognised bot chat's purge deletes that chat's and that contact's notes and every item whose run drew on them (`provenance.refs`, S3); `memory/items.py::delete_for_conversation` / `delete_for_contact` are the helpers for S03.5's deletions. The deletion card now says so (and that summaries go too, which S03.2 had already made true). **Pending owner confirmation.** | The card offers to delete what is stored about the managed chats; notes about those people belong with it. |
| D72 | **Rollup before the ceiling:** the hourly retention sweep queues `memory.refresh_summary` (immediately) for chats whose retained content is within 10 days of the 90-day ceiling and not yet covered by the rolling summary — only for accounts with `ai_managed`, never for Ignore or bot chats, and only while flag `summary.refresh` is on (the rollup is a background summary, D61). The purge never waits. `summary_gap_before` is now set only for purged content the rolling summary never covered (before S03.3 every purge set it). **Pending owner confirmation.** | ARCHITECTURE §10.4. With `summary.refresh` off (the default) there is no rollup and every purge records the gap — honest, and no background spend the owner did not turn on. |
| D73 | **Default mode for new chats: Observe** (PRD R-03, Q-06), changeable in /settings (and by `update_preferences`) to Ignore; Assist is offered from M04. A chat that starts in Ignore stores metadata only — not even the contact's name. **Pending owner confirmation.** | Least surprise; Ignore must mean nothing new is kept. |
| D74 | **Panel buttons:** Observe applies at once; Ignore asks first (in place: "new messages will not be stored; what is stored stays"), Cancel returns to the panel. Bot chats get no mode buttons and the tool refuses to set them to Observe. The "Also delete existing data" option is **not shown** until S03.5 provides `delete_conversation_data` (hook `panels.IGNORE_DELETE_OPTION`, `None`). The panel also shows the summary overview (marked AI-written) and up to 5 notes (J12). The /settings chat lists page by offset over activity order, so a page can shift while chats are active (keyset paging deferred; noted by the general review). **Pending owner confirmation.** | Ignore stops storage, the owner should see the effect before it applies; a delete button that does nothing would be a fake. |
| D75 | **Summaries see the owner's notes about that contact and that chat** (`summarize.v2`, rule 11: background only, never cited, never reported as chat content), by the §7.3 rule without any owner-scope item. The reply-drafting variant of the rule (owner preferences/style and `applies_to_replies` instructions; never owner facts) is built and tested for M04/M05. `summarize.v2` and `owner_request.v4` must pass the S03.4 E1 evaluation before the owner relies on them (no eval was run here). Catch-up period caches are not invalidated when a note changes, and forgetting a note does not rebuild a rolling summary written while it was shown (a note is never cited, so nothing in the summary can rest on it alone; the next refresh no longer sees it). Notes are shown without ids. **Pending owner confirmation.** | The only contact-facing run that exists is `summarize`; notes help it attribute ("Alex handles design") and the uncited-item guard (D65) keeps a note from becoming a "fact" of the chat. |
| D76 | **`update_preferences` covers preferred language, timezone and default mode only**, validated once for the tool, the panel and `/settings` (language codes now `xx`/`xxx` with an optional subtag, also for `/settings language`), each change audited under the account lock (FOR NO KEY UPDATE, so ingestion is never blocked); timezones must be IANA names (not `localtime`, `Factory`, `posixrules`), language codes are normalised (`EN` → `en`, `uz-latn` → `uz-Latn`). Style and tone are memory items (J11's example); reply language/tone and retention are S03.5; quiet hours and digest time M05. **Pending owner confirmation.** | Structured settings only; free text belongs in a content column, not in `accounts.settings`. |
| D77 | **The S03.1 test-only configure tool stays test-only** (`tests/integration/agent_env.py::SET_NOTE`): its scripted failures (an exception, a non-success status, a cancellation) exercise the confirmation applier's error paths, which the real tools cannot produce on demand. RG-11 now also runs with the real `remember` and `set_conversation_mode`. | Keeps the applier's failure tests without a production tool that can misbehave. |
| D65 | **Output guard and back-off:** a summary item that cites no message shown in that call is dropped as unsupported (FR-SUM-08); after 3 refused/invalid/truncated outputs in a row within 24 h, the background refresh of that chat pauses until the window passes. **Pending owner confirmation.** | No fabricated facts reach storage; a chat that reliably fails does not cost a paid call every half hour. |

## S03.4 Evaluation harness v1 (offline part)

Owner approval for this work: 2026-10-25. Branch `m03/s03.4-eval-runner`
(not pushed; an independent review comes first). **No real model and no real
Telegram call was made**: every model path is tested on `FakeLLM`. This section
is self-contained so it merges cleanly beside the S03.2 section. Update the

### Delivered

- **Runner** (`python -m evals verify|run|compare`, `evals/cli.py`,
  `runner.py`, `report.py`): refuses unless the datasets match the frozen
  manifest; runs a target; writes `docs/evals/<date>-<set>-<model>.md` and a
  `.json` beside it; `compare` tabulates quality and cost per 100 items per run.
- **Target interface** (`evals/targets.py`): `EvalTarget` (name, dataset, route,
  `uses_model`, `plan`, `run`), `MetricResult` with a pre-screen and a gate
  measure, and a marked **placeholder** `SummaryTarget` (exit code 3) for after
  S03.2.
- **Retrieval target, wired** (`evals/retrieval.py`, `corpus.py`): the real
  `memory.retrieval.search_messages` over the E1 corpus in a **throwaway
  migrated database** (`assistant_eval_<random>`, created and dropped by the
  run; `EVAL_DATABASE_URL`, default `TEST_DATABASE_URL`, never `DATABASE_URL`),
  loaded as the product stores messages (current text, tombstones for deletions,
  never `original_text`/`purged_text`). Modes: `deterministic` (no model) and
  `variants` (model-written query variants through the `LLMClient` port, then a
  final answer checked mechanically).
- **Summary-set metrics** (`evals/metrics.py`, unit-tested on hand-built
  fixtures): open-loop recall, caveat presence and spurious caveats,
  owner-facing language and script. **Judges** (`evals/judge.py`, rubrics in
  `evals/rubrics/`): fabrication pre-screen and open-loop pre-screen, behind the
  port, results *pending owner confirmation*. **Review ledger**
  (`evals/review.py`). **What a model may see** (`evals/render.py`): messages and
  coverage facts only.
- **Guards** (`evals/budget.py`, `live.py`): `--live` required for any model run;
  worst-case pre-run estimate refuses a run over the cap (default USD 1);
  in-flight hard stop; every call metered; unknown price refused; model ids from
  configuration (`--model` only to compare); no provider file, batch, feedback or
  fine-tuning API.
- **Typecheck gate** now covers `evals/` (`mypy src evals` in the justfile, CI and
  the AGENTS command table).

### Decisions (agent's choices, all **pending owner confirmation**)

| # | Decision | Why |
|---|---|---|
| E-a | **Gate versus pre-screen.** Every metric is recorded over all items (pre-screen) and over owner-confirmed items (gate). With no confirmed items, a run that stopped early, a pending judge flag or an unresolved open loop, the gate reads `NOT EVALUABLE`, never a pass. The owner's decisions live in a JSON ledger (`evals/reviews/<dataset>.json`, `--reviews`): confirmed conversation/query ids, verdicts on judge flags, covered/missed on open loops. | §10.1: gate results count only owner-confirmed items; the LLM judge only pre-screens. The datasets are frozen, so review state cannot live in them. |
| E-b | **Open-loop recall** is over open questions plus open commitments (README). An item counts as surfaced only if *every* `values` string occurs in the summary (compared in the product's ASCII form, so script, apostrophes and punctuation do not matter). **42 of the 103 open loops in E1 v1 have no `values`**, so string matching cannot decide them: the judge pre-screens them, the gate needs the owner's verdict, and without it they leave the gate open. | Conservative and honest: a looser rule would let a paraphrase-blind check pass items it cannot see. The owner may prefer adding `values` in v1.1 to ruling on 42 items. |
| E-c | **Fabrication** is an LLM-judge pre-screen only: the judge sees the chat, the `must_not_state` traps and the summary and flags statements. Every flag starts pending; only owner-confirmed flags count against the zero threshold; a conversation the judge could not screen leaves the gate open. **A judge negative decides the item:** a conversation the judge did not flag counts as clean, because the judge is the only reader that sees every summary; the owner overrides per conversation with `fabrications` in the review ledger (an owner-recorded fabrication counts as confirmed and fails the gate). Whether the owner spot-checks judge-negative summaries, and how many, is the owner's call. | Fabrication cannot be decided by string matching in the owner's language; §10.1. The judge receives labels (traps); the summariser never does. The limit of a pre-screen is stated plainly so the gate is not read as a human check of every summary. |
| E-d | **Caveats are structured output** of the summary target (gap ids named, a pre-connection flag), not parsed from prose. Presence is per conversation with expected caveats (100 %); a caveat for a gap that lost nothing (delayed-only), an unknown gap, or a pre-connection note without a coverage start is *spurious* (threshold 0). | The S03.2 renderer knows deterministically which gaps it reported; README says a delayed gap must not be reported as possibly missing. The spurious-caveat threshold is stricter than the plan's text. |
| E-e | **Owner-facing language/script** is a deterministic heuristic: at least 80 % of the letters in the owner's script, and the language (Uzbek/Russian/English) detected from a small list of function words with at least two hits and a clear winner; doubt fails. | "Correct 100 %" needs a mechanical check; it can be too strict (never too lenient). To be calibrated on real S03.2 outputs. |
| E-f | **Variants mode** uses an eval-side prompt (`evals/prompts/retrieval_variants.v1.md`) that mirrors `owner_request.v2.md` rule 5; the owner's own query is always searched with at most five variants (six in all, the service limit), top 5 results. It measures the model's variant writing plus the service, **not** the full agent loop (no tool-call format, no agent run). | An end-to-end agent run needs a control chat, consent and jobs; this is the offline, cheap version. If it clears the threshold, an agent-level spot check on the dev bot is the owner's call. |
| E-g | **"Correct final answer with reference"** is mechanical: `found`, every reference valid (a real result, a whole-word contact match, day in Asia/Tashkent, a quote that is verbatim in the message and at least 8 word characters long unless it is the whole message), at least one reference to a target message, and every `answer_values` string in the answer or quotes. A translated or reformatted value fails. The reference is read from structured fields, not free text. | No judge decides the 80 % gate. Strict on purpose; the production agent answers in free text, so this measures capability, not format. |
| E-h | A failed model call (provider error, refusal, truncation) is a **miss** and listed; a query with no hits skips the answer call and counts as wrong; queries run at a fixed instant (last message + 1 day) so the recency bonus is reproducible. | Conservative; reproducible baselines. |
| E-i | **Cost guard**: worst case = input at 1 token per character plus 500 tokens of per-call overhead, plus the full `max_output_tokens`; a run over the cap does not start; each call is refused when spent + its worst case would pass the cap; the SDK client never retries (`max_retries=0`); a call that fails with invalid output, a timeout or a connection error is billed at its worst case (a rejected request, 429 or auth, costs nothing); a model with no price is refused. Only a dated snapshot (`name-YYYY-MM-DD`) shares a base model's price; `--price` overrides match the exact model id, must be positive, and are refused for a model the product table already prices. The cap (default USD 1) is per run: the USD 1 *total* is tracked through the reports, not enforced across runs. | The cap must hold even when reasoning tokens make usage unpredictable and when attempts the provider billed return no usage. A cross-run ledger would be infrastructure for later. |
| E-j | Evaluation runs send **synthetic data only**, so their client stack has the budget wrapper but not the consent wrapper (no account, no consent row); in-memory metering, no `llm_calls` row. Requests are still labelled with honest provenance. | §14.3 guards owner data. Recorded so a reviewer does not read the missing wrapper as an omission. |
| E-k | **The gate needs every item of the set owner-confirmed.** A metric passes or fails its gate only when the owner has confirmed all `N` items of the full set (retrieval: all 38 queries; E1: every item the metric counts); it always shows "k of N confirmed". Confirmed misses that already make the threshold unreachable fail the gate earlier (a definite miss cannot be undone). A trial (`--limit`) or stopped run measures part of the set and so can never pass. | A pass on 1 of 1 confirmed items says nothing about the set. The plan's minimums (30 queries; 40 conversations) are the size of the set to be confirmed, so "the whole set" is the one threshold I can justify; the owner may prefer a smaller reviewed subset, which would be a deliberate plan change. |
| E-l | **The retrieval 85 % is a gate only with model-generated variants.** The deterministic run keeps 0.85 as a pre-screen comparison and its gate reads `INFO`. A `--limit` run is a *trial*: marked in the report and the file name (`…-trial`), limit must be at least 1, exit code 0. A run stopped on the budget cap exits with code 4 and still writes its report; a run that fails midway writes a content-free `…-aborted.json` with its spend; `--no-write` is refused with `--live`. | The plan defines the threshold with variants; a trial or a stopped run must never be mistaken for a full result; spend must never be lost with an exception. |
| E-m | **A quote must be a real excerpt**: at least 8 word characters (letters and digits, single spaces), or the whole message. | One short word or a bare amount occurs in many messages and proves nothing; 8 is about one real word plus a number. Short messages stay quotable in full. |

### Review (2026-10-25)

An independent review found the problems below; each was fixed with a failing test first (the review's test list is under *Tests*).

| Finding | Resolution |
|---|---|
| 1. Invisible SDK retries; timeouts cost $0 in the ledger | `max_retries=0`; an UNAVAILABLE failure is billed at its worst case like INVALID_OUTPUT (429, auth, bad request are not billed) (E-i) |
| 2. Prefix price match (`gpt-6-luna-pro`, `--price gpt=0:0`) | Only a dated snapshot suffix shares a price; overrides match exactly |
| 3. `--price` could override a priced model or set zero | Refused for table-priced models; zero and negative prices refused; the table is consulted first regardless |
| 4. `--limit` run complete, gate-evaluable, full-run name | `items_total`/`trial`/`stopped` on the result; trial banner, `-trial` file name, gate never evaluable; limit >= 1 (E-l) |
| 5. Gate passed on a tiny confirmed subset | Gate needs every item of the set confirmed; "k of N confirmed" always shown; early FAIL only for unreachable thresholds (E-k) |
| 6. Deterministic run carried the 85 % gate | `gated=False`: gate `INFO`, 0.85 only as the pre-screen comparison (E-l) |
| 7. Stopped run exited 0; spend lost on exceptions or `--no-write` | Exit code 4 for a stopped run; spend ledger written on any failure; `--no-write` refused with `--live` (E-l) |
| `_names_match` substring | Whole-word match |
| No minimum quote length | 8 word characters or the whole message (E-m) |
| Malformed ledger gave a traceback | `LedgerError` with the file name and field names |
| `cli.main` caught every `RuntimeError` | A dedicated `EvalsError` hierarchy (`evals/errors.py`); anything else keeps its traceback |
| `compare` showed an empty cost cell | Shows `n/a` |
| README called the cap "the S03.4 total" | Matches E-i: per run |
| E-c unclear on judge negatives | Stated plainly in E-c; owner `fabrications` override added to the ledger |
| Estimate too optimistic | 1 token per character plus 500 tokens of overhead; 1000 characters per hit |
