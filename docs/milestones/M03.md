### Decisions (agent's choices, all **pending owner confirmation**)

| # | Decision | Why |
|---|---|---|
| E-a | **Gate versus pre-screen.** Every metric is recorded over all items (pre-screen) and over owner-confirmed items (gate). With no confirmed items, a run that stopped early, a pending judge flag or an unresolved open loop, the gate reads `NOT EVALUABLE`, never a pass. The owner's decisions live in a JSON ledger (`evals/reviews/<dataset>.json`, `--reviews`): confirmed conversation/query ids, verdicts on judge flags, covered/missed on open loops. | §10.1: gate results count only owner-confirmed items; the LLM judge only pre-screens. The datasets are frozen, so review state cannot live in them. |
| E-b | **Open-loop recall** is over open questions plus open commitments (README). An item counts as surfaced only if *every* `values` string occurs in the summary (compared in the product's ASCII form, so script, apostrophes and punctuation do not matter). **42 of the 103 open loops in E1 v1 have no `values`**, so string matching cannot decide them: the judge pre-screens them, the gate needs the owner's verdict, and without it they leave the gate open. | Conservative and honest: a looser rule would let a paraphrase-blind check pass items it cannot see. The owner may prefer adding `values` in v1.1 to ruling on 42 items. |
| E-c | **Fabrication** is an LLM-judge pre-screen only: the judge sees the chat, the `must_not_state` traps and the summary and flags statements. Every flag starts pending; only owner-confirmed flags count against the zero threshold; a conversation the judge could not screen leaves the gate open. **A judge negative decides the item:** a conversation the judge did not flag counts as clean, because the judge is the only reader that sees every summary; the owner overrides per conversation with `fabrications` in the review ledger (an owner-recorded fabrication counts as confirmed and fails the gate). Whether the owner spot-checks judge-negative summaries, and how many, is the owner's call. | Fabrication cannot be decided by string matching in the owner's language; §10.1. The judge receives labels (traps); the summariser never does. The limit of a pre-screen is stated plainly so the gate is not read as a human check of every summary. |
| E-d | **Caveats are structured output** of the summary target (gap ids named, a pre-connection flag), not parsed from prose. Presence is per conversation with expected caveats (100 %); a caveat for a gap that lost nothing (delayed-only), an unknown gap, or a pre-connection note without a coverage start is *spurious* (threshold 0). | The S03.2 renderer knows deterministically which gaps it reported; README says a delayed gap must not be reported as possibly missing. The spurious-caveat threshold is stricter than the plan's text. |
| E-e | **Owner-facing language/script** is a deterministic heuristic: at least 80 % of the letters in the owner's script, and the language (Uzbek/Russian/English) detected from a small list of function words with at least two hits and a clear winner; doubt fails. | "Correct 100 %" needs a mechanical check; it can be too strict (never too lenient). To be calibrated on real S03.2 outputs. |
| E-f | **Variants mode** uses an eval-side prompt (`evals/prompts/retrieval_variants.v1.md`) that mirrors `owner_request.v2.md` rule 5; the owner's own query is always searched with at most five variants (six in all, the service limit), top 5 results. It measures the model's variant writing plus the service, **not** the full agent loop (no tool-call format, no agent run). | An end-to-end agent run needs a control chat, consent and jobs; this is the offline, cheap version. If it clears the threshold, an agent-level spot check on the dev bot is the owner's call. |
| E-g | **"Correct final answer with reference"** is mechanical: `found`, every reference valid (a real result, a whole-word contact match, day in Asia/Tashkent, a quote that is verbatim in the message and at least 8 word characters long unless it is the whole message), at least one reference to a target message, and every `answer_values` string in the answer or quotes. A translated or reformatted value fails. The reference is read from structured fields, not free text. | No judge decides the 80 % gate. Strict on purpose; the production agent answers in free text, so this measures capability, not format. |
| E-h | A failed model call (provider error, refusal, truncation) is a **miss** and listed; a query with no hits skips the answer call and counts as wrong; queries run at a fixed instant (last message + 1 day) so the recency bonus is reproducible. | Conservative; reproducible baselines. |
| E-i | **Cost guard**: worst case = input at 1 token per character plus 500 tokens of per-call overhead, plus the full `max_output_tokens`; a run over the cap does not start; each call is refused when spent + its worst case would pass the cap; the SDK client never retries (`max_retries=0`); a call that fails with invalid output, a timeout or a connection error is billed at its worst case (a rejected request, 429 or auth, costs nothing); a model with no price is refused. Only a dated snapshot (`name-YYYY-MM-DD`) shares a base model's price; `--price` overrides match the exact model id, must be positive, and are refused for a model the product table already prices. The cap (default USD 1) is per run: the USD 1 *total* is tracked through the reports, not enforced across runs. | The cap must hold even when reasoning tokens make usage unpredictable and when attempts the provider billed return no usage. A cross-run ledger would be infrastructure for later. |
| E-j | Evaluation runs send **synthetic data only**, so their client stack has the budget wrapper but not the consent wrapper (no account, no consent row); in-memory metering, no `llm_calls` row. Requests are still labelled with honest provenance. | §14.3 guards owner data. Recorded so a reviewer does not read the missing wrapper as an omission. |
| E-k | **The gate needs every item of the set owner-confirmed.** A metric passes or fails its gate only when the owner has confirmed all `N` items of the full set (retrieval: all 38 queries; E1: every item the metric counts); it always shows "k of N confirmed". Confirmed misses that already make the threshold unreachable fail the gate earlier (a definite miss cannot be undone). A trial (`--limit`) or stopped run measures part of the set and so can never pass. | A pass on 1 of 1 confirmed items says nothing about the set. The plan's minimums (30 queries; 40 conversations) are the size of the set to be confirmed, so "the whole set" is the one threshold I can justify; the owner may prefer a smaller reviewed subset, which would be a deliberate plan change. |
| E-l | **The retrieval 85 % is a gate only with model-generated variants.** The deterministic run keeps 0.85 as a pre-screen comparison and its gate reads `INFO`. A `--limit` run is a *trial*: marked in the report and the file name (`…-trial`), limit must be at least 1, exit code 0. A run stopped on the budget cap exits with code 4 and still writes its report; a run that fails midway writes a content-free `…-aborted.json` with its spend; `--no-write` is refused with `--live`. | The plan defines the threshold with variants; a trial or a stopped run must never be mistaken for a full result; spend must never be lost with an exception. |
| E-m | **A quote must be a real excerpt**: at least 8 word characters (letters and digits, single spaces), or the whole message. | One short word or a bare amount occurs in many messages and proves nothing; 8 is about one real word plus a number. Short messages stay quotable in full. |
| E-n | **What the summary target evaluates (S03.4b).** The product path `Summarizer.summarize_period` (the catch-up path), one call per conversation, **not** the rolling `refresh` (same prompt and schema, different task line; evaluating both would double the cost). Each conversation gets its own synthetic account, consents (`ai_control` + `ai_managed` naming the model's processor), connection and gap rows. The catch-up window is fixed: from one hour before the earliest of the first message, the coverage start and the first gap, until the last message plus a day (open-ended, as "until now"). `connected_at` is the dataset's `coverage_started_at`, else the window start (so no chat gets a coverage-start note unless the dataset expects one). | The catch-up is what carries the caveats and what the owner reads; one account per chat keeps one chat's coverage facts from colouring another's (the product's coverage start is account-wide). The window is the one rule under which the dataset's "refers to history before coverage" and its gaps fall inside the range the renderer is asked about. |
| E-o | **The JSON report of a summary run keeps each conversation's summary text and the judge's flagged statements** (the Markdown report stays ids and numbers). The text is model output over synthetic chats, never real data. | The owner's review ledger needs verdicts on flags, on the 42 loops with no `values` and on judge negatives; none can be given without reading what the model wrote. Ids alone made the review impossible. |
| E-p | **The caveat metric measures the wiring, not the model.** In the product the caveats are produced by deterministic code (`period_coverage` + `caveats`) and relayed by the owner-facing model (D64: "the S03.4 evaluation measures whether the final replies keep them"). The target records which gap ids the renderer carried (structured, E-d), so the metric can fail only if the gap data, the renderer or the wiring loses a caveat (a `coverage_reader` seam lets a test script that). **Both caveat metrics are therefore ungated (`INFO`, with a report note)** and kept as a wiring regression check: on E1 they are true by construction (the harness inserts the gaps from the labels it compares against) and hold even when every summary failed, so a gated "PASS" would read as the plan's threshold being measured (review finding 2). **Whether the final owner reply relays every caveat is not measured** here; that needs an agent-level run of `owner_request.v3` with the catch-up tool, a separate eval. **Likewise, recall and language are measured on the per-chat summary (the `summarize` output), not on the owner-facing reply** that the owner reads. | Honest about what 100 % means. E-d chose structured caveats because prose parsing is unreliable; the price is that the model's relay step is outside this target. Owner to decide whether the agent-level relay check is wanted before M03 closes. |
| E-q | **Owner language is a run parameter** (`--owner-language`, default `uz-Latn`), passed to the product exactly as the owner's `/settings language` value is: `accounts.locale_pref` = the tag, shown to the model as "preferred language: uz-Latn". The language check reads only the model's own words (never application text, never the English labels the judges are shown). Effort is the product's `LLM_SUMMARIZE_EFFORT` for the summarize call; the judges use the same effort. | The product accepts any short tag as language; a tag with a script is the only way to ask for Uzbek in Cyrillic or Latin. A default of Latin is a guess about the owner's preference. |
| E-r | **A conversation whose summary fails** (refusal, provider error, truncated twice, invalid output, any non-summarized status) is a miss on recall (**every open loop, whatever the ledger says**) and on language, and an *unscreened* conversation for fabrication (the gate stays open); its caveats are still reported (deterministic). **Owner coverage verdicts are keyed by loop and a digest of the summary text judged** (`c05.q2#1a2b3c4d`, `review.coverage_key`; the JSON report lists the keys), so a verdict never carries over to another run's summary. Setup failures (`no_consent`, `not_found`) raise instead: the harness is broken, not the model. The pre-run estimate prices the judges for the largest summary `sanitize` allows (≈ 27 k characters) so it is a provable upper bound; a typical run costs a fraction of it. | Same conservative rule as E-h; a refusal must not read as a clean summary. A tighter estimate would be a guess the in-flight guard could contradict. |
