## S02.1 Connection registry and consent

**Delivered:**

- Tables `business_connections` (one per account), `business_connection_events`
  (content-free history: id, rights, enabled, `change`, `source`) and
  `foreign_connections` (non-tenant cache of non-owner connections), revision
  `0004`, tested up and down by the migration suite.
- `accounts/connections.py` — the registry: owner check, lifecycle
  (`pending_owner` → `active` → `disabled`, reconnect), capability tier
  (`none` / `observe_only` / `can_reply` / `extended`), id rotation, refusal of
  late events about a replaced id, idempotence (an identical state writes
  nothing).
- `telegram/connections.py` — payload parsing (missing `rights` grants nothing;
  the legacy top-level `can_reply` is ignored), `getBusinessConnection`
  bootstrap as an inbox **preparer** that runs before the processing
  transaction, and the `CONNECTION`/`BUSINESS` handlers.
- Inbox processor: preparers per route; a handler may return a `Disposition`
  (`ignored`/`rejected`) that sets the status and clears the payload in the same
  transaction; `core.errors.TransientError` leaves a row pending without
  counting an attempt.
- Business traffic is now gated: foreign connection → `rejected`; unknown id
  Telegram cannot resolve, `pending_owner`, `disabled` → `ignored`; payload
  cleared in all cases. Live traffic is also `ignored` (payload cleared) until
  S02.2 stores it — stricter than M01, which left the payload for the 7-day
  sweep.
- Owner notices (FR-ONB-04/07) via the `connections.notify_owner(event_id)` job,
  deferred in the registry transaction and deduplicated per event: connected /
  reconnected (with "messages sent while disconnected never reached me") /
  rights changed / disconnected. Each live notice states the tier and names
  granted rights the product never uses.
- `ai_managed` consent (FR-ONB-05b, J1 step 5): asked in the "connected"
  notice when missing (pending input, 24 h), or any time with
  `/privacy managed`; recorded with policy `v2` and processor `OpenAI`.
  `/privacy` shows both consents; `/privacy revoke` already withdrew both.
- A connection that arrives before `/start` stays inert and goes live when
  onboarding consent is given, with the same notice.
- Retention: connection events 1 year; foreign connections 30 days after last
  seen.
- Privacy policy **v2 drafted** (`docs/legal/privacy-policy.md`): adds managed
  chats, the people in them, connection metadata and the second consent.

### Decisions

| # | Decision | Why |
|---|---|---|
| D27 | Bootstrap runs in the inbox (preparer), not as a job | §6.2: the update must be processed knowing whose it is, and no network call may sit inside the processing transaction. ARCHITECTURE §12.2's `connections.refresh` row was corrected. |
| D28 | Tier `none` added for a disabled connection | "No permissions" needed a name the owner and policy can read; `observe_only` would have been false. |
| D29 | Only officially documented rights count | aiogram 3.31 models `can_delete_outgoing_messages`, which Bot API 10.3 does not document (TF §13 PQ-10). Counting it would widen permissions on an unverified field. |
| D30 | Notices are a job deduplicated per event | Re-processing or a job retry must not page the owner twice; the job reloads current state so a notice never describes a superseded tier. |
| D31 | Live business updates are `ignored` with payload cleared until S02.2 | Matches the M01 plan ("business → ignored, payload cleared until M02") and keeps nothing we do not yet use. |

### Close-out work (2026-10-19)

- **Privacy policy v2 published** (owner go-ahead 2026-10-19) by editing the
  v1 page in place; the URL keeps its `-v1-` slug, the page says v2.
- **Fixtures:** the owner re-ran the sanitiser on the 2026-10-18 dump (70
  records: 13 `business_connection`, 17 `business_message`, 5 deletions,
  2 edits, 4 `getBusinessConnection` results). Every string was checked to be
  synthetic before commit. Contract tests added:
  `tests/contract/test_telegram_fixtures.py` (all observed connection payloads
  parse; a disconnect carries no `rights` and the legacy `can_reply` key grants
  nothing; `null` rights in lookups grant nothing; no business update routes to
  the control chat) and `tests/integration/test_connection_fixtures.py` (the
  observed 13-update lifecycle replays into exactly the expected history; a
  bootstrap of the replaced id after the reconnect — which Telegram answers
  with the old, disabled connection — is recorded as `stale_event` and does
  not undo the reconnect).
- **Sanitiser fix (F28):** ids were remapped per key, so one real connection id
  became `synthetic-id-…` in connection updates and
  `synthetic-business-connection-id-…` in messages, and `user.id` ≠
  `user_chat_id`. Now user/chat ids and connection ids each share one
  namespace (pinned by a new sanitiser test). The committed fixture predates
  the fix; **re-running the sanitiser** lets a contract test link messages to
  their connection.
