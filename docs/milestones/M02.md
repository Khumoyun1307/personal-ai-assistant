## S02.1 Connection registry and consent

**Delivered:**

- Tables `business_connections` (one per account), `business_connection_events`
  (content-free history: id, rights, enabled, `change`, `source`) and
  `foreign_connections` (non-tenant cache of non-owner connections), revision
  `0004`, tested up and down by the migration suite.
- `accounts/connections.py` — the registry: owner check, lifecycle
  (`pending_owner` → `active` → `disabled`, reconnect), capability tier
  (`none` / `observe_only` / `can_reply` / `extended`), id rotation, refusal of
  late events about a replaced id, idempotence (an identical state writes
  nothing).
- `telegram/connections.py` — payload parsing (missing `rights` grants nothing;
  the legacy top-level `can_reply` is ignored), `getBusinessConnection`
  bootstrap as an inbox **preparer** that runs before the processing
  transaction, and the `CONNECTION`/`BUSINESS` handlers.
- Inbox processor: preparers per route; a handler may return a `Disposition`
  (`ignored`/`rejected`) that sets the status and clears the payload in the same
  transaction; `core.errors.TransientError` leaves a row pending without
  counting an attempt.
- Business traffic is now gated: foreign connection → `rejected`; unknown id
  Telegram cannot resolve, `pending_owner`, `disabled` → `ignored`; payload
  cleared in all cases. Live traffic is also `ignored` (payload cleared) until
  S02.2 stores it — stricter than M01, which left the payload for the 7-day
  sweep.
- Owner notices (FR-ONB-04/07) via the `connections.notify_owner(event_id)` job,
  deferred in the registry transaction and deduplicated per event: connected /
  reconnected (with "messages sent while disconnected never reached me") /
  rights changed / disconnected. Each live notice states the tier and names
  granted rights the product never uses.
- `ai_managed` consent (FR-ONB-05b, J1 step 5): asked in the "connected"
  notice when missing (pending input, 24 h), or any time with
  `/privacy managed`; recorded with policy `v2` and processor `OpenAI`.
  `/privacy` shows both consents; `/privacy revoke` already withdrew both.
- A connection that arrives before `/start` stays inert and goes live when
  onboarding consent is given, with the same notice.
- Retention: connection events 1 year; foreign connections 30 days after last
  seen.
- Privacy policy **v2 drafted** (`docs/legal/privacy-policy.md`): adds managed
  chats, the people in them, connection metadata and the second consent.

## S02.2 Business ingestion and classification

**Delivered (2026-10-21):**

- `telegram/normalize.py` — pure `classify()` (ignore rules from TF §12

  `owner_manual` → `contact`) and `normalize()` (raw payload → frozen domain

  `record_message` (upsert contact and conversation, lock the conversation
  row, insert or edit the message, advance state from **new** messages only

  `record_deletion` (purge + tombstones + payload clearing),
  `record_ingest_failure` / `resolve_ingest_failure`, and

  `memory/search.py` v1 (`search_key`, script and language tags).

  unchanged, then normalize and store; Ignore mode keeps metadata only and
  clears the payload) and the dead-letter hook (`ingest_error` pause +
  `definite` gap, foreign connections create nothing).
- Poller: `system_state.last_poll_ok` and outage gaps (`possible` beyond
  24 h − 10 min, otherwise `delayed`).
- Retention: message content purged 90 days after `sent_at`/last edit with

- `/status` now receives the account's inbox backlog (the M01 wiring passed

## S02.4 Privacy baseline

**Delivered (2026-10-21):**

- **Confirmation-card primitive** (specified in S01.3, built here because
  this is the first flow with buttons): `pending_inputs.token` (revision
  `0006`, partial unique index); `accounts/service.py::create_card` /
  `claim_card` (owner-scoped, `FOR UPDATE`, single use: a double tap, a
  stale, foreign or expired token all read "no longer active");
  `telegram/control/cards.py` keyboards from `accounts/callbacks.py`; the
  `callback_query` path in `inbox_handlers.py` → `dispatcher.dispatch_callback`
  → `handlers.handle_card_press`, which always answers the press and edits
  the card in place. Plain pending text questions keep the S01.3 rules (a
  command cancels them); cards survive commands and expire after 24 h
  (swept by retention).
- **Decline / revoke flow** (FR-ONB-06, J1 step 5): declining the managed
  consent question or `/privacy revoke` (when `ai_managed` was active)
  offers card A "Delete what I stored from your chats?" [Delete] [Keep],
  then card B "How should I continue?" [Without AI] [Stop observing].
  `accounts.settings.managed_mode = stopped` makes `gate_business` ignore
  live traffic with the payload cleared; agreeing again (`/privacy managed`)
  resumes observation. The Bot API has no method for a bot to disconnect
  itself, so "Stop observing" tells the owner where to remove it (D5).
- **Deletion cascade** `privacy/deletion.py::delete_managed_data`: message
  rows, contact names, business and connection payloads, control turns that
  quoted managed content, `pending_ai_since`; one content-free audit row with
  counts. `privacy/content_columns.py` is the checked registry of every
  `text`/`jsonb` column (content vs structural); a test compares it with the
  live schema.
- **Log hygiene (RG-10 extended)**: a full scenario and injected failures
  (unique and NOT NULL violations, a deterministic error, a Telegram 400, a
  pydantic tool-argument failure, an LLM 400, a network error carrying the
  Bot API URL with the token) leave neither the canary nor the token in the
  application log; `process.py` logged `str(error)` for poller transients
  (fixed to the class name). The database side: terse error logging is
  asserted from inside the test database, set on the CI service container
  and its log is scanned for the canary after the suite.
- **Privacy policy v3** (deletion and the stop choice available; no new
  processing, so no opt-out notice — AGENTS §16); `POLICY_VERSION = "v3"`.

### M01 fix found in the M02 review (2026-10-21)

**F30 — every database error was treated as transient.** `inbox/processor.py`
caught `DBAPIError` as a whole, and `IntegrityError`, `DataError` and
`ProgrammingError` are subclasses of it: a unique or NOT NULL violation in a
handler never burned an attempt, so a poison row would retry forever, block the
queue behind it and trip the inbox liveness check. The handler also shared the
row's transaction with the attempt counter, so a half-written handler could
commit its partial rows alongside the failure count. Fix: the handler runs in a
savepoint; only deadlocks, serialization failures and connection loss are
transient (SQLSTATE 40001/40P01/08*/57P*, `OperationalError`,
`TransientError`); everything else counts an attempt; a per-route
`dead_letter_hook` runs in its own savepoint when a row is dead-lettered (S02.2
uses it to pause the conversation and record the gap). Five regression tests in
`test_ingestion.py`.
