CI stays green while a scenario fails and turns red the moment it passes, so the unit's PR must carry the marker removal and prove the behaviour. QJ1 writes from the PRD journeys, the IMPLEMENTATION_PLAN tests and the contracts, never from the implementation.

## 3. Content

### 3.1 Rules for every scenario in this package

1. **File header.** `pytestmark = pytest.mark.integration`. Each test takes one fixture (`m06_world` or `m06_env`) and builds the rest through `steps.py`.
2. **Environment.** `m06_env` calls F0-E's `p3_environment(migrated_url, flags=..., settings=...)`. If the driver has no `settings` keyword at CP1 (contract gap, QA-X §2.2 adds it), the fixture sets the values with `monkeypatch.setenv` (for example `AUTONOMY_LANGUAGES=en`) before entering the environment; the setting is function-scoped and never leaks. `m06_world` = `m06_env` with `M06_FLAGS`, `AUTONOMY_LANGUAGES=en`, the account timezone `Asia/Tashkent` and one seeded delegation over C1 only (§3.2 `delegated_chat`). A row that needs another delegation (two chats, a topic, a different limit) uses `m06_env` and seeds its own. The clock starts at the driver's `NOW` (2026-10-18 12:00 UTC = 17:00 Tashkent, outside default quiet hours).
3. **Marker.** A scenario that cannot pass on the CP1 base is `@pytest.mark.xfail(strict=True, reason="awaiting <ID>")`, where `<ID>` is the "Turns green" unit in the tables below: the unit planned to merge last among the units the scenario needs. Order by P3-interfaces §15.5, then by the README §4 slot schedule; where neither orders two units (M6-CATCH has no dependency on M6-DELEG), the table's choice stands and the marker audit (QA-X §3.8) is what corrects a wrong name, never an edit to the scenario's body. "Needs" lists the other units. **Common needs, not repeated in the tables:** every scenario that ends in an autonomous send also needs F0-S, M6-POL, DELEG-DRAFT (the real `DelegatedDraftRunner`), GRND (until it merges the contract's stubs make every reply a card: `ungrounded = 1` and every language key `None`, P3-interfaces §3.7), M6-SCHED and M6-PLAN. A scenario green on its base is unmarked. If a scenario that should be green on the base fails, the defect belongs to the F0 unit that owns the behaviour: QJ1 files it on that unit's issue with the scenario as evidence and marks the scenario `awaiting <that unit>` until the fix PR (QA-X §3.1 rule 3). `<ID>` is always a unit id from the README §3 index, never a person or a date. Parametrised cases that turn green at different merges use `pytest.param(..., marks=pytest.mark.xfail(...))` per case.
4. **A skeleton is a complete test.** The D+1.5 PR contains every scenario below with its full body. A body-less strict-xfail test would XPASS and turn CI red.
5. **Positive control.** Every scenario that asserts an absence ("never auto-replied", "nothing sent") also asserts a positive outcome in the same test (a card with a specific code, an autonomous send in a control chat, a cancelled action with a reason), so it cannot pass vacuously before the feature exists (the P2 #109 lesson).
6. **Imports.** At module level import only names that exist at CP1: `assistant.core.{flags,autonomy_texts,jobs}`, `assistant.actions.{disclosure,states,models}`, `assistant.policy.codes`, `assistant.inbox.notification_types`, ORM models, `tests.fakes.sender` (`telegram_error`, `network_error`), `tests.integration.{business_env,agent_env,p2_factories,p3_factories}`, `tests.scenarios.{p3_drive,p2_drive}`, `tests.log_hygiene`. Never import a module a later unit creates (it would break collection of the whole file). Unit behaviour is reached through ingestion, jobs, tools, cards, callbacks, commands and the poller; a direct call that cannot be avoided is imported inside the test body.
7. **Seeds.** The behaviour under test always goes through its real entry point. State the scenario does not test may be seeded with the F0-S factories (`seed_delegation`, `seed_memory_item`, `seed_autonomous_action`, `seed_owner_task`) or `p2_factories`; say so in a comment ("seeded: not under test").
8. **Determinism and data.** `FakeClock` advances only; no sleeps; interleavings use `asyncio.Event` barriers through `FakeTelegramSender.on_call` (one-shot, §3.2) and the `p2_drive.entered_or_finished` watchdog. All text is synthetic English (≥ 6 words, so the M03 tagger classifies it; lengthen a text rather than mock the tagger), except where a language is the subject. Canaries are `CANARY-SYNTH-P3-<n>`. Assertions read ids, states, reasons, codes, counts and audit `details`; message text is compared only where the text is the subject (disclosure, identity sentence, "never shown as sent"). **Notification vocabulary:** "delivered" = `notifications.status = 'sent'`; "batched" = `status = 'batched'` with the stated `reason_code`; "deferred" = `status = 'queued'` with `deliver_after` set; "settled" = any non-`queued` status.
9. **Markers come off on the unit's branch (R47).** The unit's PR never edits `tests/scenarios/m06/`. When a scenario marked `awaiting <ID>` passes on that unit's branch, CI turns red (strict XPASS); the unit's author tells QJ1 on the unit's issue and QJ1 pushes one commit to the unit's branch that removes exactly the markers of the scenarios that pass (P3-interfaces §15.1; QJ1 acts within the hour). Whichever of this PR and a unit PR is ready first merges; a unit already merged when this PR is rebased has its markers dropped by QJ1 in this PR (P2-T48). Nobody else edits a scenario; never delete or weaken one.
10. **Expected-failure classification.** Before marking, QJ1 runs each scenario unmarked on the PR base and records in the PR description the first failure point (for example "driver xfail: `replies.delegated` not registered" or "AssertionError: no scheduled action"). A failure caused by the scenario itself (fixture error, typo, wrong name) is fixed, never marked.
11. **Tool arguments.** `owner_tool` passes every field of the tool's strict args model: the schemas have no defaults, so an omitted nullable field is a validation error. Examples: `end_delegation(delegation_id=d, conversation_id=None)`; `set_conversation_mode(conversation_id=c, contact_id=None, mode=...)`; `get_activity(since=None, until=None, conversation_id=None, contact_id=None, show=None, limit=None)`; `get_status()` (no fields). `create_delegation` takes the fourteen fields of M6-DELEG §3.1 (`kind`, `chats`, `topic`, `allowed`, `notes`, `saved_note_ids`, `recipients`, `anyone_on_topic`, `starts`, `ends`, `per_chat_hour`, `total`, `urgent_in_quiet_hours`, `ai_notice`).
12. **"Card" in every table of this file means a held reply (OD-11)** when the outcome is on the autonomy side: an `agent_proposal` action in `awaiting_approval` with `delegation_id` set, `draft_flags["autonomy_codes"]` containing the named code, `draft_flags["presentation"] == "on_request"`, no `AI_MARKER` in its text and `disclosure_included = false`, plus exactly one `autonomy_not_sent` notification for it (`notsent:{id}`, `alert_class = system`, delivered at once, OD-11a) and no approval card in `control_texts` until `press_draft_reply`. A row whose steps press Approve presses `press_draft_reply` first.
