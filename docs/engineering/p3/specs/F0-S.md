## 3. Design

### 3.1 Ground rules

- Implement the two contracts exactly; invent no shared name. Where this spec and a contract differ, the contract wins and the author raises it on the integration issue before merging.
- Behaviour-neutral: nothing in F0-S writes `state = 'scheduled'`, `origin = 'delegation_auto'`, a delegation, a shareable or inferred memory item, or reads a P3 flag on a production path (only the `AutonomyConfig` builder reads `autonomy.run`, `autonomy.send`, `delegations.standing`).
- Layering stays green: `policy` and `actions/states.py` import no `sqlalchemy`/`assistant.db`; `core` imports no other assistant package; domain packages import no framework or adapter (`.importlinter`).
- Exact split so the two authors never edit the same function:

| File | J1 | J2 |
|---|---|---|
| `actions/lifecycle.py` | `_change_pending` (`delegation_ids` filter, `delegation_id` in audit details), new `cancel_pending_for_delegations` | `_event` (three events), `transition` (guards, `delegation_id`/epochs in details) |
| `automation/delegations_repo.py` | `end_delegations` | module, `DelegationView`, `active_covering`, `list_active`, `list_current`, `get` (J2 creates the file first; J1 rebases) |
| `tests/integration/test_log_hygiene_f0s.py` | `test_p3_sweep_and_deletion_log_counts_only` | the two hygiene tests of §5.2 |

### 3.4 (c) Privacy (J1)

**Registry** (P3-schema §5): `("delegations", "spec")` in `CONTENT_COLUMNS` with the given comment; the eleven new `text`/`jsonb` columns in `NON_CONTENT_COLUMNS`. `test_every_text_or_jsonb_column_is_classified` passes unchanged.

**Retention** (P3-schema §6): `PENDING_REVIEW_RETENTION = timedelta(days=14)` (OD-16), `AVAILABILITY_RETENTION = timedelta(days=90)`; `sweep_p3(session_factory, clock) -> dict[str, int]` called from `sweep_all` after `sweep_p2_rows` and before `sweep_contact_names`; per account, each in its own short transaction with an explicit `account_id` predicate: ended or cancelled delegations older than `ACCOUNTING_RETENTION`; the delegation-knowledge backstop (the exact statement in P3-schema §6); `pending_review` rows older than 14 days; then one system statement for `availability_minutes`. `SweepReport` gains `delegations`, `delegation_knowledge`, `pending_reviews`, `availability_minutes` (default 0, all in `total`). **Named touch point:** `jobs/tasks.py::JobHandlers.retention_sweep` adds the four counts to its `retention_swept` log call (counts only).

**End primitives** (P3-schema §7.1; never-edit files, J1 is their named editor):
- `actions/lifecycle.py::_change_pending` gains the keyword-only `delegation_ids: Sequence[int] | None = None` (default keeps every caller unchanged), selects `Action.delegation_id` in `RETURNING`, and adds `"delegation_id"` to the audit `details` only when the row has one (rows of other origins keep their exact details). The filter follows the existing `conversation_ids` pattern exactly: `None` = no filter; an empty sequence matches **nothing** (`IN ()`), never "every delegation" (a truthiness test here would cancel every pending action of the account).
- `cancel_pending_for_delegations(session, *, account_id, delegation_ids, reason, now, conversation_ids=None) -> list[int]` calls `_change_pending(states=PENDING, target=CANCELLED, origins=frozenset({DELEGATION_AUTO}), delegation_ids=…, conversation_ids=…)`. It never touches `executing`, an `agent_proposal` card carrying the same `delegation_id`, or another delegation's actions. An empty `delegation_ids` returns `[]` without a statement; `conversation_ids=None` means every chat of those delegations, an empty `conversation_ids` cancels nothing.
- `automation/delegations_repo.py::end_delegations(session, *, account_id, delegation_ids, reason, now) -> list[int]`: the five steps of P3-schema §7.1 in order (conditional status update `RETURNING id`; end the live links; cancel pending autonomous actions with `delegation_ended`; delete delegation-scope knowledge; one content-free `delegation_ended` audit row per ended delegation, `actor` `owner` for `owner_ended`, else `system`, `details` `{reason, to}`). Idempotent: an ended row is skipped and a second call returns `[]`. The caller holds the §9.4 locks and owns the transaction; it never enqueues anything (the catch-up request is the caller's, through `P3Ports.catch_up_requester`). `reason` must be one of `DELEGATION_END_REASONS` (anything else raises `ValueError`: a bug).

**Deletion** (P3-schema §7.2–§7.3): new `privacy/p3_deletion.py::purge_p3` (same arguments as `purge_p2`), called immediately after `purge_p2`, in the same transaction, at its four call sites in `privacy/deletion.py` (`delete_managed_data` → `managed`; `purge_conversation` → `scoped`; `_purge_chats` → `scoped`; `delete_everything` → `everything`). Every statement carries `account_id = :account_id`; delegations are locked `FOR UPDATE` ordered by id after the conversation locks the caller already holds. The seven steps per scope are the P3-schema §7.2 table, including "naming the scope" (refs or any link row, live or ended), the spec scrub (`spec = NULL` only after the active ones are ended, so `ck_delegations_active_spec` holds), the managed rules (keep the owner-authored spec), notifications whose `refs.delegation_ids` name a scrubbed delegation, and the orphan step for follow-ups and one-off reminders (`rrule IS NULL`) whose task is gone. `DeletionReport` gains `delegations_ended`, `delegations_deleted`, `automations_cancelled` (in `counts()` and `total`); `purge_p3`'s `memory_items`, `tasks`, `automations`, `notifications` are added to the existing counters. `receipt_text` adds `{delegations_deleted} delegation(s)` to the "Deleted:" list, then "Delegations ended: N." and "Reminders and follow-ups cancelled because their task was deleted: N." only when non-zero; ended is never reported as deleted (invariant 11).

**Post-restore** (P3-schema §8): step 2b in the post-restore transaction right after step 2, per account: lock active delegations `ORDER BY id FOR UPDATE`, `end_delegations(..., reason="restored_from_backup")`; the notice payload gains `"delegations_ended": {"<account_id>": <count>}`; `PostRestoreReport.delegations_ended` (the sum). **Named touch point:** `inbox/backup_check.py::deliver_restore_notice` adds, after the skipped-schedules line and only when the count is > 0: "{count} delegation(s) were ended because of the restore. Set them up again if you still want them." Nothing re-activates a delegation; a second post-restore changes nothing.
