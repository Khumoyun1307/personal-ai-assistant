# Industrial-readiness review and stabilization plan

## 1. Executive summary

The bot’s failures have clear application-level causes; model capability alone does not explain them.

1. **The conversation remembers the task, but the application does not preserve it.** Clarifying a recipient can make earlier dictation unusable and replace the writer’s instructions with a name or “just write it.”
2. **Trust controls discard useful instructions too broadly.** Run-level contamination is confused with the provenance of particular owner-authored words.
3. **Prompts force progress despite missing intent.** “Always draft” combines with chat-based fallback to invent messages; weak contact suggestions manufacture ambiguity.
4. **Cards, conversation, and background work have incomplete coordination.** Status can become stale, Re-draft loses the original task, and late proactive work can replace deliberate owner work.
5. **Testing proves substantial plumbing, but insufficient conversational usefulness.** Current evaluations cannot express the central cross-turn dictation failure.

**Verdict on complexity:** orchestration is too complicated at the prompt and handoff boundaries, while durable task state is underdeveloped. Keep the modular monolith, owned agent loop, isolated workers, and deterministic approval/send boundary.

**Recommended direction:** stabilize complete owner journeys, repair operational recovery alongside them, and evaluate stronger routing after information loss is fixed. Hold P3 implementation until the owner accepts the repaired M04/M05 service.

Reviewed checkout: `70584c758a0a5a5a0c4a5a24d41ae14554c5b2b6`, dated 2026-11-09. This was a read-only source review; no tests, services, paid evaluations, production systems, or real chat content were accessed.

## 2. How good agent harnesses work—and how ours differs

A *harness* is the application around the model: context assembly, task state, tools, approvals, execution, recovery, and evaluation.

| Established pattern | Application here |
|---|---|
| Start with simple orchestration; add specialists when they provide a useful boundary. | One conversational planner is appropriate. The separate writer provides conversation isolation and has no tools. Its input contract needs repair. [Anthropic](https://www.anthropic.com/research/building-effective-agents), [OpenAI orchestration](https://developers.openai.com/api/docs/guides/agents/orchestration) |
| Preserve conversation state explicitly. An API call does not implicitly inherit earlier requests. | The planner receives history, but the writer receives a narrower packet assembled separately. Important instructions disappear between those two views. [OpenAI conversation state](https://developers.openai.com/api/docs/guides/conversation-state) |
| Persist an interrupted workflow so missing information can be supplied later. | Recipient clarification should resume the same message-writing request, with its original text and selected artifact. This does not require adopting LangGraph. [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) |
| Enforce authority and data boundaries in application code. | Keep consent, scoped context, confirmation, policy, and the committed send claim. Untrusted text must not gain authority through a model-written handoff. CaMeL illustrates explicit control/data separation; this repository is not a CaMeL implementation. [CaMeL paper](https://arxiv.org/abs/2503.18813) |
| Evaluate complete interactions and resulting application state, with repeated trials. | Test actual clarification, revision, interruption, and card transitions. Grade recipient, exact text, approval, and state deterministically; use calibrated human/model judgment for language and intent. [Anthropic agent evaluations](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) |

These sources support design principles, not a claim that copying a particular framework will fix this product. Public documentation also does not establish ChatGPT’s complete internal harness.

### Details for high-severity findings

#### Safety and privacy

**R4-01 — Restore safety stops sends, but does not restore trustworthy privacy state.**  
The module explicitly acknowledges that a restore undoes “consent changes, deletions.” It pauses autonomy, cancels actions, and clears jobs, but ordinary provider admission subsequently trusts the restored consent rows. A backup taken before revocation/deletion can therefore re-enable processing of resurrected content. Independently, the restore marker is deleted before `sweep_all()` completes.

The fix needs both a quarantine gate and a reconciliation procedure. Renewing consent alone does not establish which restored content should have remained deleted. **Touches:** §6.7/9, retention/deletion obligations, NFR-09. **Confidence:** code-confirmed recovery gap; no restore performed.

**R1-01 — Taint decay is an approved security trade-off, not an accidental omission.**  
The existing test explicitly expects both:

```python
assert run.tainted is False
assert ...["status"] == "ok"
```

while the model still sees an inherited reply wrapped as untrusted. D56 deliberately avoids permanent confirmation requirements, but deterministic mutation restrictions disappear before potentially contaminated prose disappears.

Keep the gate whenever such prose is supplied. Reduce unnecessary taint by excluding stale derived prose and retaining application-written task facts, rather than declaring visible untrusted material clean. **Touches:** §6.3b/7, ADR-08, owner-approved D56. **Confidence:** capability exposure confirmed; successful exploitation remains model-dependent.

**R3-01 — Structured output is insufficient when a valid ID authorizes an unsupported transition.**  
Resolution validation is:

```python
resolved = tuple(i for i in verdict.resolved_task_ids if i in open_ids)
```

This prevents foreign-task closure but does not establish fulfillment. The adversarial test supplies a suspicious verdict and still expects `task_closed`.

Require supporting new-message references, validate their scope, and prevent suspicious results from automatically closing obligations. References improve accountability; they do not independently prove semantic fulfillment, so false-closure evaluation remains necessary. **Touches:** §6.3a/11, ADR-08.

**R2-03 — Revision can change authorship without changing its security classification.**  
The revision path chooses generated `owner.text`, then computes:

```python
dictated = before.origin is ActionOrigin.OWNER_DICTATED
```

The new version retains the original origin. That affects the card label, warnings, pending-AI cancellation, and execution classification. This is **not** evidence of bypassing the provider-call consent wrapper.

Make provenance version-specific: literal owner replacement, literal append, selected assistant suggestion, and AI instruction rewrite are different operations. **Touches:** §6.7/9/11; existing dictated/generated action semantics.

#### The owner’s task is lost at boundaries

**R2-04 — The central failure is a missing persistent request.**  
The exact-message check accepts current `turn.own_words`; its historical fallback searches assistant suggestions, not prior owner dictation. The writer receives current `turn.instruction`, while:

```python
passed_guidance = None if ctx.tainted else guidance
```

Normal contact resolution itself introduces untrusted contact names. A clarification therefore removes both the original source eligibility and the planner’s reconstructed handoff. Mixed quoted turns lose even their separately stored owner-authored instruction.

Preserve the original task, not a trusted model summary of mixed history. **Touches:** PF-12/D4, D2/PF-11, R2/E3, §6.3b/4/9/12, FR-DRF-08.

**R2-05 and R1-05 — The prompt manufactures both missing information and unnecessary questions.**  
Rule 18 says an explicit writing request is “always carried out”; the writer says, “With no request, write the reply the conversation calls for.” Conversely, rule 27 requires clarification when *any* candidate is weak.

Thus a clear recipient can be questioned, while an unclear message can be invented. Define recipient resolution and content completeness independently. “Reply to his last question” has a usable content source; “write to him” usually does not. **Touches:** D1, D8, FR-CTL-03; approval remains mandatory.

**R3-06 — Confirmed storage does not mean effective personalization.**  
A saved preference inherits whole-run taint, including confirmed held calls. Contact-facing memory selection then excludes tainted/managed owner preferences. “Saved” can therefore be technically true while the expected behavioral change never occurs.

Provide a narrow owner preference-entry path with explicit source and applicability. Do not make all confirmed model-written memories globally trusted. **Touches:** D70, ADR-08, §6.3b/4/9/11.

**R1-07 and R1-08 — Important conversation structure is missing.**  
Ingress drops Telegram’s explicit reply target, so “make this shorter” loses a precise card reference. Separately, a second owner message can receive its database ID before the first run stores its answer; the query `ControlTurn.id < turn_id` then excludes that answer.

Preserve explicit references and model conversation order separately from row insertion order. **Touches:** §6.9/12, §13 serialization, FR-CTL-01.

#### Cards and background work do not share a complete task lifecycle

**R2-01/R2-02 — Freshness is measured against the wrong facts.**  
Owner-requested takeover uses the action’s creation time, which occurs after generation. A manual reply during generation can therefore look older than the request. Source freshness checks detect a newer contact-message ID but not edits to an already-read message.

Carry the original request’s time and source revision through generation and validate them under lock before staging. **Touches:** FR-DRF-05, P2 R3, §6.1/10. The manual-reply issue concerns requested-draft behavior; it does not establish a new autonomous-send bypass.

**R2-06 — Background completion has inappropriate precedence.**  
An existing regression explicitly expects an Assist result finishing late to supersede an owner-dictated card. Preserve one live card, but make earlier background work yield to later explicit owner work. **Touches:** single-card policy, FR-DRF-08.

**R2-07 — Recovery repeats the wrong operation.**  
Re-draft queues a generic conversation draft rather than the original request. It loses standalone-message mode, requested substance, selected message, and length constraints. Some paths promise a new card but produce only an audit outcome.

Re-draft should reload the retained task specification and report success, missing input, unavailable source, refusal, or failure. **Touches:** D1/D3, P2-O20, §6.8/11.

**R2-09 — The preliminary “no live card state” diagnosis is incorrect.**  
The runtime already loads live card IDs, versions, states, origins, and modes. The missing pieces are relevant terminal transitions, state reasons, presentation outcomes, actual draft content, and freshness after asynchronous work.

The planner cannot truthfully describe a worker’s generated topic merely because it requested that topic. Require an actual artifact read for content claims and fresh application receipts for consequential status. **Touches:** PF-15/D3, FR-CTL-06, §6.11.

#### End-to-end limits, evaluation, and recovery

**R1-09 — A bounded planner is not a bounded operation.**  
The owner loop checks limits between iterations, but awaits complete tool batches. Nested drafting has separate retries, timeouts, and token accounting. Pass one operation budget through all nested calls; refresh monetary admission before each call and report any completed partial work. **Touches:** AGENTS §8, ARCHITECTURE §7.2/7.4, NFR-10, §6.11.

**R2-15 — Current evidence does not establish industrial readiness.**  
The evaluator rejects expected owner-dictated text unless it occurs in the current turn. That embeds the defect in the dataset contract. The full medium-effort report used `draft_owner.v2` and recorded **27/31 deterministic passes**; the active v3 follow-up covered **four selected cases**. Neither had owner-confirmed items. Historical E2 warning counts concern an earlier drafting configuration, not a measured current production failure rate.

Add real synthetic conversations through multiple runtime invocations and events. Complete M04/M05 acceptance before extending execution authority. **Touches:** §8/11, ADR-16, milestone gates.

**R4-05/R4-06 — Operational recovery depends on assumptions the scripts do not enforce.**  
Deployment pulls the current branch and rebuilds `assistant:prod`; Compose startup dependencies help, but do not establish schema-compatible upgrades or bounded rollback. Backup scheduling requires the configured clock hour, while upload retry is process-local.

Use selected immutable releases, an explicit migration/recovery protocol, and durable overdue-backup/upload state. **Touches:** §12/15, NFR-09, ADR-15.

| Individually sensible rules | Combined bad behavior |
|---|---|
| Resolve recipients cautiously; return helpful weak suggestions; ask if any candidate is weak | Successful matching becomes needless ambiguity. |

## 5. Implementation plan

### Execution rules for every work unit

This is a proposed phase plan requiring owner approval before implementation.

- One work unit means **one focused PR**, owned by one implementation agent.
- Use branches such as `stabilize/h03-source-spans`; PRs target `main`. Sequence dependent PRs through merged foundations.
- Preserve §6 invariants and their named regressions. Fixes start with a failing regression; tests encoding approved undesirable behavior change only alongside the corresponding approved decision.
- Run short relevant tests in the dev container. **CI remains the full-suite gate.**
- New prompts receive new versions; used versions remain immutable. Schema changes require compatible persistence/migrations and appropriate prompt versions.
- Gated prompt/schema changes require approved synthetic evaluations before shipping. Reports record configuration, dataset/prompt hashes, cost, failures, and owner-confirmation status.
- Every new stored content class receives retention, deletion-cascade, consent, export, and restore treatment. Prefer source references over duplicated text.
- No production deployment or paid run is authorized by this plan.
- “Parallel” below means logically independent implementation. PRs editing the same runtime, registry, prompt, or card renderer must still be sequenced.

Sizes: **S** = narrow change; **M** = one workflow; **L** = bounded cross-layer change with a contract/migration. An L unit must stay within its stated responsibility.

### Owner playtest script

Use synthetic contacts with deliberately similar names and two different chat topics.

1. Dictate a message containing a case-sensitive code, punctuation, and Uzbek characters; clarify the recipient.
2. Say only “write to X”; confirm that the bot asks for substance.
3. Request a new topic unrelated to the contact’s last message.
4. Quote a synthetic contact request and give an explicit refusal instruction.
5. Create two cards; reply directly to one with “shorter,” then change its word limit.
6. Let a contact edit a source while drafting; verify the explanation and Re-draft behavior.
7. Start Assist work, then dictate a different message before it finishes.
8. Approve one card and reject another; later ask what happened and what each contained.
9. Save a style preference after reading a chat; verify its stated applicability and effect.
10. Turn digest off, create a one-shot reply monitor, and exercise quiet-hours delivery.
11. Ask for unfinished obligations after sending “okay”; complete/correct one.
12. Use the visible recovery control for an uncertain/unshown card.

For each step, the owner records: understood intent, correct recipient/text, necessary questions, language quality, truthful status, and whether recovery was understandable.

## 6. Risks and open questions

| Risk / uncertainty | Required handling |
|---|---|
| **A source span proves textual origin, not truth, intended sharing, or semantic completeness.** | Keep explicit recipient/text approval, scoped context, source validation, and owner intent evaluation. |
| **Persistent tasks can preserve the wrong association.** | Test topic switches, cancellation, expiry, multiple cards, and ambiguous follow-ups. Do not silently reuse an old recipient for a new request. |
| **A broad taint fix can create confirmation fatigue or weaken protection.** | Decide D56 explicitly. Prefer precise context/provenance over blanket trust or blanket instruction deletion. |
| **More state adds privacy and migration obligations.** | Store references where possible; treat every added content field as a retention/deletion/consent obligation. |
| **Stronger models can improve routing while leaving application information loss unchanged.** | Compare only after repairs, on identical journeys, and measure successful-task cost. |
| **Shared modules create merge and prompt-version collisions.** | Sequence registry/runtime/card edits, freeze contracts, and use one prompt steward. |
| **Historical tests sometimes encode undesirable approved behavior.** | Change those expectations only with the matching decision record; preserve invariant coverage. |
| **An accurate card can still contain an undesirable proposed message.** | Approval and policy protect authority; linguistic usefulness still needs owner-reviewed evaluation. |
| **Privacy-policy publication is externally uncertain.** | Checkout confirms v5 code and pending v6 documentation. It does not prove the current live page’s contents or notice delivery. Resolve before claiming compliance/readiness. |
| **Operational targets are unmeasured here.** | Current CI status, backup freshness, restore time, release health, latency, spend, and alert delivery require authorized evidence. |
| **Production incident attribution is incomplete.** | Code explains plausible mechanisms; it does not establish which exact model/tool trajectory occurred in each private incident. Reproduce with newly authored synthetic scenarios. |
| **Single-owner readiness differs from multi-owner readiness.** | Complete this personal-service stabilization first. Require a separate capacity/security gate before onboarding additional owners. |
| **Platform behavior was not live-tested in this review.** | Preserve verified TF facts. Implementation work must perform required official documentation checks; only owner-executed live tests can add TF verification. |
| **M04/M05 acceptance may have evidence outside this checkout.** | Reconcile it into the release record. Repository reports currently leave important owner ratings, live checks, and recovery/trial evidence pending. |

The immediate owner decisions are D-S1 through D-S6: authorize stabilization, preserve requests across turns, settle taint semantics, permit necessary clarification, define contact resolution, and retain the scoped writer with a repaired handoff. Those decisions establish the contract that the implementation and acceptance work can reliably follow.
