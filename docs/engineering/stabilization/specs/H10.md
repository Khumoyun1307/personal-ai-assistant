| Acceptance ID | Exact criterion |
|---|---|
| H10-1 | C6 content revision advanced once for meaningful input change, not duplicate/idempotent no-op; privacy/retention changes participate under same conversation lock. |
| H10-2 | Application-issued fence stores observed revision **with** read data. Main multi-chat reads union dependencies; mixed revisions force consistent reread/stale. Model cannot supply a fresh revision for old text. |
| H10-3 | New contact arrival or edit/delete base/non-base while FakeLLM paused yields stale rejection at settlement under account→sorted conversations→request→action order. No lock held across provider/network. |

| H10-5 | Explicit retained older target permitted; missing/foreign/deleted/purged target unavailable, never latest fallback. Owner literal standalone retains own-source proof and minimal target/takeover checks. |
| H10-6 | Legacy NULL fence does not imply fresh generated content. Migration up/down, source-scope deletion/text cleanup and content registry pass; fences never pin content. |
| H10-7 | I3 receives content revision/invalidation seam for changed IDs behind coverage cursor; H11 receives owner-intent counter field, without implementing I3/H11 semantics here. |
