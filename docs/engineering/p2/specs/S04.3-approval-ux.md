## 1. Goal

The owner sees every proposed reply as a card in the control chat — who it goes to, what it answers, the exact text, until when it can still be sent — and approves, edits or rejects it with one tap. A tap changes state **exactly once**; an approved card hands the action to the executor in the same transaction; every later state change (sent, failed, uncertain, outdated, expired, cancelled) shows on the card; when sending is impossible, the card offers copy-ready text.

## 2. Scope

**In:** `telegram/control/approvals.py` (card view loader, renderer, keyboards, the `act` callback handler, the `draft_edit` pending-input handler, `ApprovalCards` implementing `ApprovalCardPresenter`); the `replies.revise` job; `system.expire_actions`; `system.sync_action_cards`; the revising reconciler; registration of the `act` kind, the `draft_edit` input and the jobs in `_wire_m04` and `jobs/tasks_actions.py`; the **M04 `owner_request` prompt bump** (P2-T17).

**Out:** policy rules (S04.1); the executor and its outcome texts' state changes (S04.4 — this unit renders whatever state S04.4 records); drafting itself (S04.2); `/activity` (S04.5).

## 3. Design and implementation requirements

### 3.1 Card view and rendering

`load_card_view(session, *, account_id, action_id) -> ApprovalCardView | None` (account-scoped) reads: the action (state, reason, origin, kind, version, text, `draft_flags` (decisions R8), `expires_at`, `executed_at`, `error_class`); the conversation and contact (`memory/summaries.py::preferred_name`); the **triggering messages**: the contact messages after the last owner/assistant message up to `base_message_id`, at most 3, newest last, each cut to 300 characters; the owner's timezone.

`render_card(view, *, timezone) -> (text, keyboard)` — HTML through the control renderer, every protected content field escaped exactly once before composing application markup (tag-shaped text defused first); the gateway preserves its entities without turning escaped tags into markup. This is the ICR-5 / #131 correction to P2-T54's earlier gateway-only escaping implementation; entity-looking literals remain literal too. Bidi/invisible characters are made visible (line breaks kept) as the S03.1 confirmation cards do (`agent/confirmations.py` helpers). Layout:

1. A header that says what this is and is never confusable with a sent message (FR-ACT-02): e.g. "📝 Draft reply — awaiting your approval" (agent proposal), "📝 Message you dictated — check the recipient and the text" (owner-dictated), "📝 Assist draft" (proactive).
2. "To: <contact name>" (escaped).
3. "Answering:" with the triggering excerpts (escaped, marked as the contact's words).
4. The exact text of the current version (escaped), visually separated.
5. "Sendable until <local time>" (`expires_at`; for an autonomous action `min(expires_at, window close − margin)`; owner's timezone) or "Not sendable: <reason>". An owner-approved live card whose window estimate is closed adds "⚠️ <name> hasn't written in the last 24 hours, so Telegram may not allow this send." and stays approvable; after Telegram refuses (`expired`/`window_closed`, `error_class = window_closed`) the state line is "Not sent — Telegram didn't allow this send (the contact hasn't written in the last 24 hours)" with copy-ready text (owner decision 2026-10-30, P2-O20).
6. Warnings from the action's `draft_flags` column (never from `policy_decision`): "Contains a commitment (date, amount or promise) — check it" when `makes_commitment`; "Sensitive topic" when `sensitive_topic`. Owner-dictated actions have no flags and no warnings.
7. State line using the F0 labels (`actions/states.py`): Sending…, Sent ✓ 18:05, Not sent — <reason>, Delivery uncertain — please check the chat, Outdated — <reason>, Expired — <reason>, Rejected, Cancelled — <reason>.

**Length:** a card is one control message (≤ 4096 after rendering). If the text part would push it over, TL decision (spec): send the full text first as a separate plain control message (no buttons), and the card says "Full text in the message above (N characters)"; the card keeps the first 600 characters as a preview. The approval still binds to the action's version, and the executor sends exactly the stored text.

**Keyboards by state** (callback kind `act`, F0-interfaces §7; ≤ 64 bytes):

| State | Buttons | Token |
|---|---|---|
| `awaiting_approval` | Approve (`ok`) · Edit (`ed`) · Reject (`rj`) | `actions.approval_token` |
| `revising` | Cancel edit (`cx`) | a `pending_inputs` card, kind `act`, `ref_id` = action id |
| `outdated`, `expired` (agent proposal) | Re-draft (`rd`) + copy button | a `pending_inputs` card, kind `act` |
| `blocked`, `failed`, `expired`/`outdated` (owner-dictated) | copy button only | — |
| `succeeded`, `delivery_uncertain`, `rejected`, `cancelled`, `approved`, `executing` | none | — |

**Drafts-only mode (P2-T21):** with `actions.send` off, every card behaves normally (Edit, Reject, Cancel edit, expiry, outdating, Re-draft); only Approve leads to `blocked`/`sending_disabled`, rendered as "Not sendable — sending is turned off" with the copy-ready text. The explanation text for `sending_disabled` comes from `actions/states.py` (F0).

**Copy-ready (FR-DRF-06):** if the text has 1–256 characters, an inline button with `copy_text` (Bot API `InlineKeyboardButton.copy_text: CopyTextButton`, `CopyTextButton.text` 1–256 characters — docs-checked by the TL from the Bot API reference; re-check https://core.telegram.org/bots/api#copytextbutton and aiogram 3.31's `CopyTextButton` type before coding, AGENTS §2); otherwise the card says "Copy the text above" (the text is already in the card or the message above). Button styling beyond the S01.3 primitives is optional; do not rely on an undocumented field.

### 3.2 `ApprovalCards` (the `ApprovalCardPresenter`)

- `present_after_commit(session, action_id)`: registers an `after_commit` action that loads the view, sends the card (`gateway.send_text(ControlChat, …, keyboard=…)`), and records `card_message_id` and `card_state` in a new short transaction **only if** the action's state and version are still those rendered (otherwise the sync fixes it next minute).
- `sync_after_commit(session, action_id)`: after commit, loads the view and edits the card in place (`edit_control_text`), then sets `card_state = state` on a definite result. "Message is not modified" counts as success.
- **ICR-5 / #131 replay correction:** before any new full-text/card presentation, commit an account/version/state/card-fenced audit claim. An unresolved claim blocks automatic replay, including after crash or failed final commit; a different action/version may proceed. Resolve `shown` atomically with truthful complete-card recording, or `not_delivered` only for a definite first-send refusal before any prefix/full text was delivered. Full-text success plus a later card refusal remains partial/uncertain, never restarting its full text. No business-action state change or lock across Telegram. Exact event shapes are in F0-interfaces §11.

### 3.3 The `act` callback handler (`handle_action_press`)

Registered in `ControlRoutes.callbacks["act"]`. Runs in the inbox processor's transaction (ARCHITECTURE §6.7 as built S02.6): **all database work in the transaction, every Telegram call through `db.uow.after_commit`**, the press always answered.

Resolution and locking:
1. The dispatcher already resolved the account from `from.id`; a press from anyone else never reaches here (it gets "no longer active" — test it).
2. Find the action by token **within the account**: first `actions.approval_token`, else a `pending_inputs` card of kind `act` (`accounts/service.py::claim_card` semantics). Not found ⇒ answer `CALLBACK_EXPIRED_TEXT` ("This card is no longer active").
3. Lock in the §9.4 order: account `FOR SHARE`, the action's conversation `FOR SHARE`, then change the action **only through S04.1's transition functions** (`approve`, `reject`, `start_edit`, `cancel_edit` — decisions R7): each is one conditional `UPDATE … WHERE id = :id AND account_id = :a AND state = :expected [AND approval_token = :token] [AND version = :v]`, audited by the transition itself (F0-interfaces §11, R15). This unit writes **no `UPDATE` of `actions.state` of its own**; it may set `card_state`/`card_message_id` in the same transaction. A transition that did not apply ⇒ "no longer active". This is what makes a double tap one transition (RG-04).

Operations:
| Op | Valid in | Effect |
|---|---|---|
| `ok` | `awaiting_approval` (token = `approval_token`) | `actions.lifecycle.approve(session, account_id=…, token=…, now=…)` (S04.1: checks the token and `expires_at > now`, sets `decided_at`, `approved_text_hash`, writes `action_approved`). `APPROVED` ⇒ `card_state = 'approved'`; **defer `actions.execute(action_id)` in the same transaction** (transactional defer: `connection=` the raw driver connection, as `dispatcher.py` does for owner turns); after commit answer **"Sending…"** when `ActionsConfig.sending_enabled`, else **"Approved — sending is off"** (never "Sending…" when nothing can be sent; decisions R17) and edit the card (no buttons). With sending off the path is otherwise the same (P2-T21): Tx A ends the action `blocked`/`sending_disabled` and the sync shows "Not sendable — sending is turned off" with the copy-ready text (the M04 live window part 1 relies on this). `EXPIRED` ⇒ the card shows Expired with copy-ready text. `NOT_ACTIVE` ⇒ "no longer active". If the commit fails, nothing is announced (the press is answered with an error by the processor's failure path) |
| `ed` | `awaiting_approval` | `start_edit` (S04.1: → `revising`, token voided, `action_revision_requested`); create the Cancel card token; `set_pending_input(kind="draft_edit", ref_id=action_id, ttl=min(expires_at − now, 1 h))`; card edited to the revising view: "Send the new text, or tell me what to change" + Cancel edit |
| `rj` | `awaiting_approval` | `reject` (S04.1: → `rejected`/`owner_rejected`); card shows Rejected |
| `cx` | `revising` (Cancel card) | `cancel_edit` (S04.1: → `awaiting_approval`, same text and version, a **new** `approval_token`, `revision_turn_id` cleared); clear the `draft_edit` input; card back to the approval view |
| `rd` | `outdated`/`expired` agent proposals (Re-draft card) | `actions.drafts.request_draft(reason=REDRAFT, …)` for the conversation (S04.2: **no flag; deferred inside this press transaction** with queueing lock `redraft:{conversation_id}` inside a SAVEPOINT, so it cannot be lost and a conflict cannot abort the press; test `test_a_second_redraft_tap_while_one_is_queued_keeps_the_press_transaction_alive`; the job re-checks consent, "not Ignore" and the window); answer "Drafting a new version…"; the old card keeps its final state |

### 3.4 Edit: the `draft_edit` pending input and `replies.revise` (P2-T08)

**Input handler** (`ControlRoutes.pending_inputs["draft_edit"]`; the dispatcher never passes a forwarded/third-party message to a pending input, M03 D49):
1. Load the action within the account; it must still be `revising`; otherwise clear the input and tell the owner the card is no longer being edited.
2. Store the owner's message as a control turn (`accounts/service.py::record_control_turn`, role `owner`, `refs = {"conversation_ids": [conv], "contact_ids": [contact]}` so deletion of that chat redacts it; `contains_managed = False` — the owner's own words), and record it on the action with S04.1's `set_revision_turn(..., expected_version, turn_id)` → `actions.revision_turn_id` (decisions R8).
3. Defer `replies.revise(action_id, turn_id)` in the same transaction, inside a SAVEPOINT (queueing lock `revise:{action_id}`; a conflict must not abort the edit — F0-interfaces §6.1 rule; the revise reconciler via `revision_turn_id` covers anything lost); clear the input; answer "Revising…" and edit the card to "Revising…".

**`replies.revise` job** (`jobs/tasks_actions.py`, queue `llm`, no `lock`, no retry):
1. `Drafter.revise(account_id, action_id, turn_id)` (S04.2) — consent and budget re-checked there.
2. New text: `revision_kind == "replacement"` ⇒ the owner's turn text **verbatim** (from `control_turns.text`, never the model's output); `"instruction"` ⇒ the run's `text`.
3. In one transaction with the §9.4 locks: S04.1's `apply_new_version(..., expected_version=v, text=new, draft_run_id=run, draft_flags=<the run's flags>, shown_through_message_id=…, base_message_id=…)` — conditional on `state = 'revising' AND version = :v`, version + 1, fresh token, `revision_turn_id` cleared, writes `action_edited`; **`expires_at` is never extended, only shortened if the window now closes earlier** (the one expiry rule, decisions R7). `STALE` (outdated, expired or cancelled meanwhile) ⇒ discard, nothing else changes — so **a revision finishing late never changes what was or will be sent**. Then `sync_after_commit`.
4. `TOO_LONG` / `EMPTY` (R7): the row stays `revising`; clear `revision_turn_id` (`set_revision_turn(..., turn_id=None)`), re-open the `draft_edit` input, and tell the owner "That text is too long (N characters; the limit is 4096) — send a shorter one or Cancel edit" / "That text is empty". No version is created, so nothing over 4096 characters ever becomes approvable (no partial send, ARCHITECTURE §9.3).
5. Run failed (refused, invalid, no consent, over budget): S04.1's `revision_failed` (→ `awaiting_approval` with the previous text and version, a fresh token, `revision_turn_id` cleared); the card says the draft could not be revised and is unchanged.

**Revising reconciler** (`jobs/reconcile_actions.py`): actions in `revising` whose `revision_turn_id` is set, with no `todo`/`doing` `replies.revise` job, revising for more than 5 minutes ⇒ re-defer `replies.revise(action_id, revision_turn_id)` once; after 30 minutes ⇒ `revision_failed` with the note. An action in `revising` with no `revision_turn_id` (the owner never answered) expires normally.

### 3.5 Expiry and card sync (periodic, queue `system`)

- `system.expire_actions` (every minute): calls S04.1's `expire_due(session, now=…)` — actions in `awaiting_approval`/`revising`/`approved` that are due, with reason `window_closed` when an autonomous action's window is closed now, else `max_age` (one rule, one reason order, decisions R7; owner-approved actions are never expired by the window estimate, owner decision 2026-10-30, P2-O20). Never `executing`. Audits come from the transitions. Clears `draft_edit` inputs of expired actions, then `sync_after_commit` for each.
- `system.sync_action_cards` (every minute): (a) actions with `card_message_id` and `card_state IS DISTINCT FROM state` ⇒ edit (index `ix_actions_card_unsynced`); an edit is idempotent, so retry next minute after a failure; stop after 10 failures and log; (b) actions in `awaiting_approval`/`revising` with `card_message_id IS NULL` and created more than 30 s ago ⇒ present (covers a crash between a proposal's commit and its card).

### 3.6 The M04 `owner_request` bump (P2-T17)

This unit writes `agent/prompts/owner_request.v<N+1>.md` = the version active on `int/m04` **word for word** plus the M04 rules, except sentences M04 makes false, which are replaced (v8: 'you cannot send' and 'Assist mode is not available yet' — P2-T54), and switches the registry entry; old versions stay. Rules (not wording):
1. To answer someone in a chat: `propose_reply` (the assistant drafts) or `propose_message` (the owner's own words, passed exactly). Never state or imply that anything was sent: relay each tool's `status` as it is (awaiting approval, blocked with its reason, not drafted).
2. Dictated text is passed exactly as the owner wrote it; if the recipient is ambiguous, resolve it (`resolve_contact`) and ask one question rather than guess.
3. One card per chat: a new proposal replaces the earlier card (say so when it happens).
4. "Stop replying"/"pause" ⇒ `pause_autonomy`; resuming happens only via `/resume` or the card button (S04.4's rule text).
5. "What did you send/draft?" ⇒ `get_activity`; relay sent, awaiting, failed and uncertain exactly; mention assistant activity listed in a catch-up (S04.5's rule text).
Collect the S04.4 and S04.5 rule texts from their PR descriptions. TL decision (spec): if S04.4 or S04.5 merge after this unit, Viro makes one final small PR `m04/owner-request-bump` after them instead of bumping twice. After the bump: the retrieval agent-mode eval is re-run (`--estimate-only`, `--limit 1`, full; ≈ USD 0.10–0.15; owner go-ahead; Antony or the TL runs it; results in `docs/evals/`).

## 6. Acceptance criteria

1. Every proposal shows a card with contact, triggering messages, exact text, sendable-until and Approve · Edit · Reject (FR-DRF-03); state changes update it in place.
2. A double tap or a stale or foreign token never causes a second transition (RG-04).
3. Approve defers execution atomically with the transition; nothing is announced if the commit fails.
4. Edit accepts replacement text (kept verbatim) or an instruction (FR-DRF-04); Approve is impossible while revising; late revisions change nothing; an over-long revision never becomes a version; every state change goes through S04.1's transitions (R7).
4a. With `actions.send` off, Approve answers "Approved — sending is off" and the card ends "Not sendable — sending is turned off" with copy-ready text (P2-T21, R17).
5. Cards expire at max age (autonomous ones also at window close) with copy-ready text, and a send Telegram refuses for the window ends with copy-ready text (FR-DRF-05/06, owner decision 2026-10-30, P2-O20); outdated cards offer Re-draft.
6. The `owner_request` bump is active, older versions kept, and the retrieval re-run is recorded.
7. All tests in §5 exist and pass in CI; ruff, format, mypy, `lint-imports` clean; logs content-free.

## 8. Risks

- **Card and state drift** — the card sync makes the card eventually true; tests cover changes made outside the card flow.
- **Long drafts** — the "full text above" path is tested; the executor never splits business messages.
- **Prompt bump collisions** — only this unit bumps `owner_request` in M04 (P2-T17).
