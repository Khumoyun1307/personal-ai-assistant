## 1. Goal

A reliable scheduler for owner-local recurring work, built once and reused by M07: due occurrences are claimed exactly once in an occurrence ledger, fire late with a note or are skipped, survive restarts and restores, and follow the owner's timezone. Its first user is the **daily digest**: delivered at the owner's chosen local time, once per period, composed deterministically from what P2 already knows. `/digest` gives it on demand.

## 2. Scope

**In:** `automation/rules.py` (`ScheduleRule`, `DigestRule`); `automation/schedules.py` (reconciler, firing, lifecycle, digest-automation sync); `system.reconcile_schedules`; `automation.fire`; `inbox/digest.py` (`build_digest`) and `digest.build`; `telegram/control/digest.py` (`/digest` command, digest rendering); post-restore step 4; flag `digest.daily`.

**Out:** reminders, follow-ups and scheduled summaries as products (M07 — the core here supports them, no owner-facing creation in P2); monitors (S05.4, event-only automations); a model-written digest (P2-T13); deletion/retention for these tables (F0 — verify only, §3.8).

## 3. Design and implementation requirements

### 3.1 Rules (`automation/rules.py`)

```python
class ScheduleRule(RuleBase):  # schema_version = 1; the schedule itself lives in columns
    schema_version: Literal[1] = 1
    max_lateness_minutes: int  # after this, an occurrence is skipped with a note


class DigestRule(ScheduleRule):  # kind "digest"; no content
    kind: Literal["digest"] = "digest"
```
The schedule is in the row's columns (`rrule`, `run_at`, `timezone`, `tz_policy`, `next_run_at`), interpreted with S05.3a's `ScheduleSpec` (`dtstart_local` = the automation's first local occurrence, stored in the spec as `"YYYY-MM-DDTHH:MM"`; add `dtstart_local: str | None` to `ScheduleRule`). A row that fails to load (`ValidationError`, `ScheduleError`) is set `paused` with audit `automation_invalid` and never fires (fail closed).

### 3.2 Reconciler — `system.reconcile_schedules` (every minute, `system` queue, qlock = name)

One transaction (`automation/schedules.py::reconcile_due(session, now, limit=100)`):
1. **Digest sync** (TL decision (spec) — keeps S05.2P free of schedule code): for each active account, compare its digest preference (`digest_time`, `accounts.timezone`) with its `kind = 'digest'` automation: create it (status `active`, `rrule = "FREQ=DAILY"`, `tz_policy = 'follow_owner'`, `timezone = account.timezone`, `dtstart_local` = today at `digest_time`, `next_run_at` = `next_occurrence(after=now)`, `confirmed_at = now`) when absent and `digest_time != "off"`; update time/timezone and recompute `next_run_at` when they differ; set `paused` when `"off"`; reactivate when turned back on. Only while flag `digest.daily` is on.
2. **Timezone changes:** active `follow_owner` automations whose `timezone` ≠ the account's → `rezone` (S05.3a) and recompute `next_run_at` from now (`fixed` untouched, ARCHITECTURE §12.4).
3. **Due rows:** `SELECT … WHERE status = 'active' AND next_run_at <= now ORDER BY next_run_at FOR UPDATE SKIP LOCKED LIMIT :limit`. For each: `occurrence_at = next_run_at`; `lateness(occurrence_at, now, grace=2 min, max_lateness=rule.max_lateness_minutes)`; `INSERT INTO automation_occurrences (… status) VALUES (…, 'claimed' | 'skipped') ON CONFLICT (automation_id, occurrence_at) DO NOTHING` with `note_code = 'late'` for LATE, `'skipped_obsolete'` for SKIP; advance `next_run_at = next_occurrence(spec, after=occurrence_at)` (and past `now` for a skipped run of several missed occurrences: record one `skipped_obsolete` row per missed occurrence up to 10, then jump to the next future occurrence); `last_run_at = now`; `None` → `status = 'completed'`, `ended_at`. Expired (`expires_at <= now`) → `status = 'expired'`, `ended_at`.
4. After the commit, defer `automation.fire(automation_id, occurrence_at)` for each inserted `claimed` row (qlock `auto:{id}:{epoch}`). A conflict means a job exists — not an error.
Because the occurrence row is inserted and `next_run_at` advanced in the same transaction, a reconciler run while an occurrence is executing finds `next_run_at` already in the future and never re-defers it.

### 3.3 Firing — `automation.fire(automation_id, occurrence_at)` (`outbound` queue)

1. Load the occurrence; `fired`/`skipped` → no-op (idempotent).
2. Re-check: automation still `active` (or completed by this very occurrence), account active, kind-specific flag on.
3. Kind `digest`: defer `digest.build(account_id, period_end = occurrence_at)` (qlock `digest:{account}:{epoch}`). Other kinds: no product handler in P2 → mark `skipped` with `note_code = 'no_handler'` (M07 adds handlers).
4. `UPDATE automation_occurrences SET status = 'fired', fired_at = now WHERE id = :id AND status = 'claimed'`.
Delivery dedupe never depends on step 4: digests dedupe on the `digests` row (§3.5), other kinds on `notifications.dedupe_key = 'auto:{automation_id}:{occurrence_epoch}'` (ARCHITECTURE §12.4). A crash after delivery and before step 4 → the re-run finds the delivery deduplicated and only marks the occurrence `fired`.

### 3.4 Digest content (`inbox/digest.py::build_digest`, deterministic, P2-T13)

Inputs for one account and period `[period_start, period_end)`, where `period_start` = the previous `sent` digest's `period_end` (or `period_end − 24 h`, at most 48 h back):
1. **Needs you** — standard notifications of kinds `triage_urgent`/`triage_decision` created in the period that were `batched` or are still deferred, one line per chat: contact name, the verdict's first reason.
2. **Waiting for your reply** — the attention list (S05.1 `triage_store.latest` + v1 selection), up to 10 chats.
3. **Commitments due** — open `contact_commitment` tasks with `due_at < period_end + 24 h` (J7 step 2: "a contact commitment with a due time that is still open at that time appears in the next digest") and open `owner_commitment` tasks due in the same window: title, contact, local due time.
4. **Closed automatically** — tasks closed with `resolved_by_triage` in the period (FR-TRI-05, ARCHITECTURE §10.3 "reported in the digest").
5. **Other alerts** — counts of the remaining `batched` notifications by kind.
5a. **Deletions** (owner decision E2, 2026-10-26: every deletion is noted in reports and summaries) — per chat, how many messages were deleted in the period (`messages.deleted_at` in the period, split into the contact's, the owner's and the assistant's sent messages; Telegram does not say who deleted them — TF §12 LV-07 — so the digest never says), and any owner data deletion in the period (`data_deleted` audit rows: scope and time, counts only). Only when non-empty.
6. **Coverage** — `memory.catch_up.period_coverage` + `caveats` for the period (gaps, connection off intervals), only when non-empty.
7. Nothing in 1–5 → one line: "Quiet day — nothing needs you." (still sent: the owner learns the digest works).
Rendering (`telegram/control/digest.py`): HTML with names and titles escaped; times in the owner's timezone; split by the existing control renderer; no message text of contacts (only reasons and titles the product already shows). English fixed texts (P2-O11).
**"Open chat" buttons (R17):** the digest message carries one "Open: <contact>" button per chat in sections 1–2, at most 5 (the first ones listed), on the last chunk. They are a `pending_inputs` card of the S05.2 `ntf` kind with op `op` (or a digest-specific card kind registered in `ControlRoutes` if `ntf`'s `ref_id` = notification id does not fit — decide with Jack and record it in the PR); the handler re-checks the chat belongs to the presser before sending its panel. Buttons on model-written attention-list and catch-up replies remain an open item (S05.2 §8).

### 3.5 `digest.build(account_id, period_end)` (`llm` queue; at most once)

1. Claim: `INSERT INTO digests (account_id, period_start, period_end, status) VALUES (…, 'building') ON CONFLICT (account_id, period_start, period_end) DO NOTHING RETURNING id`. On conflict: an existing row `sent`/`uncertain`/`failed` → no-op; `building` older than 10 minutes (a crash before the send) → take it over with a conditional update on `updated_at`; younger → no-op.
2. Build (§3.4) in a read transaction; collect the batched notification ids it covers.
3. Before sending: `UPDATE digests SET status = 'uncertain' WHERE id = :id AND status = 'building'` and `mark_digested(ids, digest_id)` (S05.2) in one transaction — the at-most-once claim (same pattern as S05.2 §3.2: a crash after this point never resends).
4. Send through `ControlChannel`. Record: ok → `sent`, `sent_at`, `message_id`, audit `digest_sent` (counts only); definite failure → `failed` (the next day's digest covers the period again because `period_start` follows the last **sent** digest); uncertain → stays `uncertain`.
A digest built twice for one period is therefore delivered once.

### 3.6 `/digest` (P2-T20, `CommandHandler` registered under `digest` in `ControlRoutes`)

Builds and sends a digest now for `[last sent period_end or now − 24 h, now)` through the same §3.5 path (`period_end = now` rounded down to the minute, so a double tap within the minute is one digest). Batched alerts it includes are marked digested, so the evening digest does not repeat them. It works whether or not `digest.daily` is on (it needs only an onboarded account and reads only what exists). The product has no `setMyCommands` call and P2 adds none (F0-interfaces §7): this unit adds exactly one line for `/digest` to the `/help` text in `telegram/control/handlers.py` (the allowed exception, R12).

### 3.7 Post-restore step 4 (`privacy/post_restore.py`, ARCHITECTURE §15.6)

In the post-restore transaction: for every `active` automation with `next_run_at < now`, insert `skipped` occurrences with `note_code = 'skipped_restore'` for the missed occurrences (at most 10 per automation) and recompute `next_run_at = next_occurrence(after=now)`. The owner notice (existing) gains one line: "N scheduled items were skipped because of the restore." Test: `test_post_restore.py::test_post_restore_skips_past_occurrences_with_a_note_and_reschedules`.

### 3.8 Privacy (verify, do not re-implement)

F0 created retention for `automations` (ended + 1 year), `automation_occurrences` and `digests` (1 year), and the deletion cascade (automations naming a deleted chat/contact are deleted; `delete_everything` deletes every automation except kind `digest`, R11). Add one test proving the digest automation survives `delete_everything` and a deleted chat's tasks never appear in the next digest.

## 6. Acceptance criteria

1. Occurrences are claimed exactly once, fire late with a note within `max_lateness`, are skipped with a note beyond it, survive restarts and restores (FR-FUP-08).
2. DST and timezone tests of IMPLEMENTATION_PLAN S05.3 pass.
3. A digest per period is delivered at most once; uncertain never resent; failures covered next time.
4. The digest arrives at the configured local time (M05 checklist §5: five consecutive days, CP5).
5. `/digest` works on demand.
6. All tests green in CI.

## 8. Risks

- **Double digests or missed days** — the `digests` unique row, the uncertain claim and the period rule; the five-day live check proves it.
- **Timezone edge cases** — S05.3a's tests plus §5's DST tests on the real reconciler.
- **Digest noise** — a quiet day is one line; the owner can turn the digest off in `/settings` (S05.2P).
