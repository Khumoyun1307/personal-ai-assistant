## 1. Goal

An approved reply is sent **at most once**, only after a fresh policy check under row locks, to exactly the chat it was approved for, with exactly the approved text — and every outcome (sent, not sent, uncertain) is recorded and reported truthfully (AGENTS §6 invariants 1, 6, 7, 8, 10, 11; NFR-06). The owner can stop autonomous activity instantly (`/pause`), and no send is ever decided on state that lags behind updates Telegram already holds.

## 2. Scope

**In:**
1. Gateway business methods and `telegram/business_targets.py` (F0-interfaces §4), plain-text business sending, global throttle, an explicit Bot API request timeout.
2. `actions/executor.py`: Tx A (claim + execution-phase policy) → gateway call → Tx B (outcome), exactly ARCHITECTURE §9.4; the `actions.execute` job; error-class → state mapping; `assistant_sent` message records.
3. The ingestion barrier (poller side): the `caught_up_at` write for the **current process run** that S04.1's reader expects (F0 writes the per-run reset before any role starts — decisions R1).
4. `system.mark_uncertain`; `DELIVERY_UNCERTAIN` and `CONNECTION_STALE` owner alerts (via `OwnerAlerts.notify_owner` until CP4), including their two fixed texts in `inbox/notify.py` (an allowed edit, decisions R12).
5. The actions reconciler (lost `actions.execute` jobs).
6. Kill switch: `/pause`, stop word, the poller fast lane; `/resume`; `pause_autonomy` and `resume_autonomy` tools.
7. Call sites that change send-relevant state: connection disabled / rights changed / stale, `ai_managed` revoked, dead-lettered business update. (Mode → Ignore is S04.2's, in `conversations/modes.py` — decisions R12; this unit does not edit that file.)
8. RG-12 guards (gateway edit/delete of assistant messages only), confinement test for business sends.
9. `/status` actions block.

**Out:** cards, card sync, expiry job, edit loop (S04.3); drafting, the ingestion listener's outdating on new messages (S04.2); autonomous sending, delegations, delays, `actions.release_scheduled` (M06); notifications table delivery (S05.2 moves the alerts at CP4); Undo feature (R3).

## 3. Design

### 3.1 Gateway (`telegram/gateway.py`, `telegram/business_targets.py`)

- `TelegramSender` gains `send_plain_message(*, chat_id, text, business_connection_id)`, `edit_plain_message_text(*, chat_id, message_id, text, business_connection_id)` and `delete_business_messages(*, business_connection_id, message_ids)`; `AiogramSender` implements them **without `parse_mode`** (draft text is never interpreted as HTML; contact- or model-influenced text cannot inject formatting or links). The existing HTML methods stay control-chat only. `FakeTelegramSender` implements the same, records every argument (F0 already records `business_connection_id`), and scripts errors with `fail_with`.
- `BusinessTargetResolver.resolve(account_id, conversation_id) -> BusinessTarget | None` (short read-only session): the account's `business_connections` row with `status = 'active'` and `is_enabled`, and the conversation (account-scoped, `kind = 'business'`, contact not a bot) → `BusinessTarget(connection_id, chat_id = business_chat_id)`. Anything missing → `None`.
- `OutboundGateway.send_business_text(*, account_id, conversation_id, text) -> SendResult`: resolve → if `None`, return `SendResult(BAD_REQUEST, error_code="local_target_refused")` **without calling Telegram**; else throttle (per chat ≈ 1/s, plus a global minimum interval of 40 ms between any two sends — ARCHITECTURE §6.8 "< 25 msg/s"; **TL decision (spec)**) → one `send_plain_message` → `SendResult(OK, message_id=<returned id, may be 0>)` or the classified failure. Never splits, never logs text or URLs; logs `account_id`, `conversation_id`, `message_id`, `error_class`, `error_code`.
- `edit_assistant_message` / `delete_own_business_messages` (RG-12): resolve the target; for every ref, require a `messages` row of that conversation with `direction = 'assistant_sent'`, not deleted, with a non-NULL `telegram_message_id`; otherwise return `BAD_REQUEST`/`local_target_refused` without calling Telegram. No product feature calls them in P2 (P2-T10).
- `send_text(BusinessChat, …)` keeps raising `BusinessSendNotAvailableError` (business sends go only through `send_business_text`).
- **Request timeout:** `bootstrap.py` creates the `Bot` with an explicit aiogram session timeout of **20 s** for Bot API calls (today it uses the library default). It must stay below the outbound queue's 30 s shutdown grace so an in-flight send finishes and Tx B commits on SIGTERM. **TL decision (spec).**

### 3.2 Executor (`actions/executor.py`) and the `actions.execute` job

The executor depends on ports only (`actions.ports.BusinessSender`, `ApprovalCardPresenter`, an alert port, `JobScheduler`); `bootstrap.py` wires the gateway, S04.3's presenter and `OwnerAlerts`.

```python
async def execute(action_id: int) -> ExecuteOutcome:
    # ---------------- Tx A: claim under locks (ARCHITECTURE §9.4 step 1) ----------------
    async with transaction(sf) as uow:
        keys = SELECT account_id, conversation_id FROM actions WHERE id = :id          # no lock; finds the keys
        if keys is None: return NOT_FOUND
        SELECT … FROM accounts      WHERE id = :a FOR SHARE
        SELECT … FROM conversations WHERE id = :c AND account_id = :a FOR SHARE
        # (delegations FOR UPDATE: M06, autonomous origin only)
        action = SELECT … FROM actions WHERE id = :id FOR UPDATE
        if action.state != APPROVED:                       return NOOP(action.state)   # double defer / settled
        if action.retry_at and action.retry_at > now:      redefer_at(action.retry_at); return NOT_YET
        ctx = await load_context(..., phase=EXECUTION, ai_generated=action.origin is AGENT_PROPOSAL)
        decision = decide(ctx)
        action.policy_decision = as_json(decision)
        match decision.outcome:
            case WAIT:                                     # inbox not drained / barrier not passed
                after_commit(redefer, at=now + 3 s);       return WAITING
            case DENY:
                target = execution_target(decision)        # S04.1 mapping; None = already claimed
                if target: transition(APPROVED → target.state, reason=target.reason)
                presenter.sync_after_commit(action.id);    return DENIED(target)
            case ALLOW_AUTO:                               # "may send now" (S04.1 §3.2)
                attempt = uuid4().hex
                transition(APPROVED → EXECUTING, values={attempt_id: attempt, attempt_started_at: now,
                                                         sent_text_hash: sha256(action.text)})
                claim = Claim(action.id, account_id, conversation_id, action.text, action.version, attempt)
    # commit here: the claim is durable BEFORE Telegram is called (invariant 6)
    # ---------------- the call, outside any transaction (step 2) ----------------
    result = await sender.send_business_text(account_id=claim.account_id,
                                             conversation_id=claim.conversation_id, text=claim.text)
    # ---------------- Tx B: record the outcome (step 3) ----------------
    async with transaction(sf) as uow:
        SELECT … FROM conversations WHERE id = :c FOR UPDATE      # §9.4 order: conversation, then action
        row = SELECT … FROM actions WHERE id = :id AND attempt_id = :attempt
                                     AND state IN ('executing','delivery_uncertain') FOR UPDATE
        if row is None: log("tx_b_no_matching_attempt"); return          # never retry, never resend
        late = row.state == DELIVERY_UNCERTAIN
        apply_outcome(row, result, late)                                   # table below
    presenter.sync_after_commit(claim.action_id)                           # card shows the truth
```

**Outcome mapping (Tx B):**

| `result.error_class` | Action | Other effects | Audit |
|---|---|---|---|
| `OK`, `message_id > 0` | `→ succeeded` (`sent`), `telegram_message_id`, `executed_at` | Upsert the `messages` row: `INSERT … (account_id, conversation_id, telegram_message_id, direction='assistant_sent', observed_via='new', sent_at=now, content_type='text', text, content_hash, search_key/script/lang_guess as ingestion computes them, action_id) ON CONFLICT (conversation_id, telegram_message_id) DO UPDATE SET direction='assistant_sent', action_id=EXCLUDED.action_id` — an echo processed first is absorbed (LV-03: none observed, branch kept fail-closed); `conversations.last_assistant_msg_at = max(…)`, `availability = 'active'` | `action_succeeded {version, attempt_id}` |
| `OK`, `message_id == 0` | `→ succeeded`, `telegram_message_id = NULL`, `identity_pending = true` | Insert the `messages` row with `telegram_message_id = NULL` (NULLs are distinct: two such sends in one chat both succeed); the ingestion classifier's identity-pending echo rule (§6.5) can fill the id later | `action_succeeded {identity_pending: true}` |
| `RATE_LIMITED` | `→ approved`, `retry_at = now + retry_after` (default 3 s if absent), `attempt_id` cleared | After commit, defer `actions.execute` at `retry_at`. After 5 rate-limited attempts on one action → `failed` (`not_delivered`) instead (**TL decision (spec)**; counted from `action_rate_limited` audit rows) | `action_rate_limited {retry_after}` |
| `WINDOW_CLOSED` | `→ expired` (`window_closed`), `error_class`, `error_code` — `executing → expired` is a legal transition (decisions R4; this unit adds it to the ARCHITECTURE §9.4 diagram) | — | `action_expired` |
| `PEER_UNAVAILABLE` | `→ failed` (`not_delivered`), codes | `conversations.availability = 'possibly_paused'` (§6.6) | `action_failed` |
| `CONNECTION_INVALID` | `→ failed` (`connection_invalid`), codes | `accounts.connections.mark_stale(session, account_id, now)`: `business_connections.status = 'stale'` + audit `connection_marked_stale` (time = stale since). Every other approved action then fails Tx A on `connection_active`/`connection_stale` (business sends blocked for the account). A new id from a `business_connection` update or an unknown-id bootstrap reactivates it (`_classify` already maps stale → `RECONNECTED`) | `action_failed` |
| `CHAT_UNREACHABLE`, `FORBIDDEN`, `BAD_REQUEST`, `CONFLICT` (incl. `local_target_refused`) | `→ failed` (`not_delivered`), codes | — | `action_failed` |
| `AMBIGUOUS`, `TRANSIENT` | `→ delivery_uncertain` (`ambiguous`) | After commit: `notify_owner(DELIVERY_UNCERTAIN, dedupe_key=f"uncertain:{action_id}")` (class system). **Never retried** | `action_delivery_uncertain` |

A late definite result for a row already `delivery_uncertain` (same attempt) **does not use the table above** (decisions R4): `OK` (either `message_id` case) → `succeeded` with the same message-row upsert; **any definite failure — including `RATE_LIMITED` and `WINDOW_CLOSED` — → `failed`** (`not_delivered`, codes kept; never back to `approved`, never retried); `AMBIGUOUS`/`TRANSIENT` → stays `delivery_uncertain`. The transition writes `action_late_result` and the card is updated (ARCHITECTURE §9.4 step 3). Nothing ever moves `delivery_uncertain` to `approved`, `executing` or `expired`.

**Exceptions:** an exception **before** Tx A commits propagates; the job may retry (bounded, DB-transient only). An exception **after** the claim (gateway raising unexpectedly, Tx B failing) is caught and logged; the row stays `executing` and `mark_uncertain` settles it. A re-run job always stops at "state != approved", so even an unexpected retry cannot send twice.

**Job** (`jobs/tasks_actions.py`): `actions.execute(action_id)` on queue `outbound`, no `lock`, no queueing lock (Tx A orders it); retry strategy: at most 3 attempts, only for `OperationalError`-class DB errors raised before the claim; never `retry=True`.

### 3.3 Ingestion barrier (ARCHITECTURE §9.4 "Ingestion barrier")

The barrier is **bound to the process run** (decisions R1 — the blocking review finding: a barrier written by the poller's own startup could still read "passed" from the previous run while roles start concurrently):
- **F0** generates `process_run_id` (uuid4) in `bootstrap.running_process` and, **before any role starts**, commits `system_state['ingestion_barrier'] = {"process_run_id": <id>, "caught_up_at": null}` (key name from S04.1). The id is injected into the poller and into the executor (which passes it to S04.1's `load_context`/`ingestion_state`).
- The first `getUpdates` after startup uses `timeout=0`.
- The first `poll_once` of this run that returns fewer than `limit` updates (Telegram's queue is drained) sets `caught_up_at = now` **for this run** — `UPDATE … WHERE value->>'process_run_id' = :own_run_id` — in the same transaction as the batch insert (or alone, for an empty batch). A poller never writes `caught_up_at` for another run id.
- S04.1's `ingestion_state` treats the barrier as passed **only** when the stored `process_run_id` equals the executor's own and `caught_up_at` is set; with `pending_inbound == 0` the rule `inbox_drained` passes. Until then Tx A answers `WAIT` and the job re-defers itself in 3 s; past `expires_at` it expires instead.
- Fail closed: a database with no running poller (restored scratch), a key left by a previous run, or a process started **without the poller role** (`--roles` leaving it out: its run id is never caught up) never sends. Splitting the poller and the worker into separate processes is R4 work and changes this rule then.

### 3.4 `system.mark_uncertain` and alerts

- Periodic, every minute, queue `system`, queueing lock = name (`jobs/tasks_actions.py`). One statement: `UPDATE actions SET state='delivery_uncertain', state_reason='stale_executing', updated_at=now WHERE state='executing' AND attempt_started_at < now − threshold RETURNING id, account_id, version, attempt_id` plus one `action_delivery_uncertain` audit row per action with `{from, to, version, reason, attempt_id}` (the same event and details the transition primitive writes, F0-interfaces §11, decisions R15); `threshold = max(MARK_UNCERTAIN_AFTER_SECONDS, 20 s request timeout + 10 s throttle wait + 30 s)` = 120 s by default. After commit: `DELIVERY_UNCERTAIN` alert per action (dedupe per action) and card sync.
- Same job: for each account whose connection is `stale` with `connection_marked_stale` older than `CONNECTION_STALE_ALERT_MINUTES` and still stale, `notify_owner(CONNECTION_STALE, dedupe_key=f"connection_stale:{account_id}:{stale_since_epoch}")`, once per stale period.
- Alert texts (fixed, English; this unit adds the two entries to the `inbox/notify.py` text table — an allowed edit, decisions R12): delivery uncertain — "I'm not sure a reply reached <contact>: Telegram did not confirm it. Please check the chat. I will not resend it." (contact name rendered at delivery from ids; never message text); connection stale — "Telegram stopped accepting replies through the old connection and no new one has arrived for 30 minutes. Open Chat Automation in Telegram and check Alviro is connected."

### 3.5 Actions reconciler (`jobs/reconcile_actions.py`)

Registered `Reconciler` (F0-interfaces §6.3): `approved` actions with (`retry_at IS NULL OR retry_at ≤ now`) and `updated_at < now − 10 s`, with no `actions.execute` job for that `action_id` in `todo`/`doing` → `DeferRequest(EXECUTE_TASK, {"action_id": id})`. Safe by construction: Tx A's conditional claim prevents a second send. (Lost defer after an approval commit — ARCHITECTURE §9.5 — is covered here.)

### 3.6 Graceful shutdown

The supervisor stops the poller, drains the inbox, then stops workers (existing). The `outbound` worker's 30 s graceful timeout covers an in-flight send (20 s request timeout + Tx B). Test that SIGTERM during an in-flight send still commits Tx B. A send cut off anyway leaves `executing` → `mark_uncertain` on the next start (honest, never resent).

### 3.7 Kill switch (PRD J9, FR-AUT-06, R-09)

- **What `/pause` means in M04** (no delegations exist): `accounts.autonomy_paused = true`; pending actions with origin `delegation_auto` → `cancelled` (`autonomy_paused`) via a new helper `actions.lifecycle.cancel_autonomous_pending(session, account_id, now)`; Tx A denies autonomous origin while paused (rule `autonomy_not_paused`); **owner-approved actions are not affected** — they carry the owner's explicit approval of that text (PRD §12.2 #1: "/pause blocks autonomous sends only"). Decided as P2-T23 — the PRD's "owner-approved sends still require a fresh approval" is read as "approval is always required", not "existing approvals are voided".
- **Acknowledgement after commit** (ARCHITECTURE §9.4 "The /pause acknowledgement is sent only after its transaction commits"): the existing `/pause`, `/resume` and stop-word branches in `telegram/control/dispatcher.py` move their reply into `db.uow.after_commit`. This is the one edit S04.4 makes to dispatcher.py (an allowed exception in F0-interfaces §12; the consent-revoke call site in `handlers.py` is the other). Honest text: "Paused: no automatic replies until you send /resume. Replies you approve are still sent." / "Resumed."
- **Poller fast lane** (ARCHITECTURE §6.1): in `write_batch`'s transaction, for each update that is a private `message` with `from.id == chat.id`, `from.id` in `OWNER_TELEGRAM_IDS` (the poller receives the allowlist from `bootstrap.py`), no forward markers (`forward_origin`, legacy `forward_*`, `is_automatic_forward`), and whole text `/pause` (optionally `@<bot username>`) or a stop word (`telegram/control/handlers.is_stop_word`): `UPDATE accounts SET autonomy_paused = true WHERE telegram_user_id = :from AND status = 'active'` (and `cancel_autonomous_pending`). The inbox processes the message normally later (idempotent) and sends the acknowledgement. There is no Pause *button* in M04 (none exists yet; M06 adds one to delegation cards) — **TL decision (spec)**.
- **`/resume`** only by the command or a card button; it clears the account flag only (per-conversation takeover pauses stay, R-09).
- **Tools** (`agent/tools/autonomy.py`, registered with flags `tool.pause_autonomy`, `tool.resume_autonomy`, class `control`, `owner_request`, `CONTROL_ONLY`, `returns_managed=False`): `pause_autonomy` (no args) does what `/pause` does and returns `{"status": "paused"}`; it is in `TAINT_EXEMPT_TOOLS`, so it runs in a tainted run; idempotent. `resume_autonomy` (no args) is in `CARD_ONLY_TOOLS`: every model call becomes a confirmation card (existing gate); the model gets `awaiting_confirmation`; only the owner's tap runs the handler (via `agent.apply_confirmation`), which clears the flag and returns `{"status": "resumed"}`.

### 3.8 Call sites that change send-relevant state

All run inside the existing transaction of the triggering change, after taking the §9.4 locks that path already takes; card refreshes are left to S04.3's sync.

| Trigger | Where | Call | Reason |
|---|---|---|---|
| Connection `DISABLED` | `accounts/connections.apply_snapshot` | `cancel_pending(account_id, None)` | `connection_disabled` |
| Connection `RIGHTS_CHANGED` | same | `outdate_pending_for_account(account_id, include_approved=True)` (new helper, S04.4) | `rights_changed` |
| Send result `CONNECTION_INVALID` | executor Tx B | `mark_stale` (other approved actions then fail Tx A); audit `connection_marked_stale` | `connection_invalid` |
| `ai_managed` revoked | `telegram/control/handlers.handle_revoke` (and any other revoke path) | `cancel_pending_ai_generated(account_id)` (new helper: origin `agent_proposal` only; owner-dictated texts are not AI content) | `consent_revoked` |
| Dead-lettered business update | `conversations/service.record_ingest_failure` | `outdate_pending(account_id, conversation_id, include_approved=True)` | `ingest_error` |

(Mode → Ignore is not in this table: S04.2 makes that call in `conversations/modes.py`, decisions R12.)

Note on the dead-letter row: ARCHITECTURE §6.2 says "its pending actions are outdated" when a business update for the chat is dead-lettered (the chat may hold an unseen takeover or contact message). `ingest_error` **is** a `StateReason` (F0-interfaces §2; no ICR needed — decisions R17); its explanation: "A message in this chat could not be processed, so I cannot be sure this draft is still current." Tx A additionally refuses while the conversation is paused with `autonomy_paused_reason = 'ingest_error'` only for autonomous origin (rule `autonomy_not_paused`); owner-approved actions created after the dead letter are judged by the normal rules.

Takeover and new contact messages are handled by S04.2's `ActionsIngestionListener` (outdating) **and** independently by Tx A's `no_takeover_since`/`not_stale` (the guarantee). S04.4's tests cover the Tx A side with and without the listener present.

### 3.9 `/status` actions block (`observability/status.py`)

`StatusReport` gains `actions: ActionsStatus(awaiting_approval, sending (approved+executing), uncertain_7d, failed_24h)` (counts only); `/status` renders one line ("Replies: 2 awaiting approval · 0 sending · 1 delivery uncertain — check the chat"); `get_status` returns the same report.

### 3.10 Confinement

Extend the banned-call AST test so that, in `src/`, `send_business_text`, `edit_assistant_message` and `delete_own_business_messages` are called only from `actions/executor.py` (definitions in `telegram/gateway.py` and protocols in `actions/ports.py` excepted), and `send_plain_message`/`edit_plain_message_text`/`delete_business_messages` only from `telegram/gateway.py`.

### 3.11 Edge cases (each has a test in §5)

Two `actions.execute` jobs for one action; approval committed but defer lost; process killed between claim and send; Tx B after `mark_uncertain`; echo before Tx B; two `message_id == 0` sends; 429 with and without `retry_after`; window closing between approval and Tx A; owner message dated after the base but ingested after the action was created; `/pause` and a takeover waiting in Telegram's backlog at restart; connection id rotated while an action is approved; a 5 000-character approved text (seeded) — blocked, no partial send; a dead-lettered update in the chat; SIGTERM mid-send; a 5-minute owner run on `llm` while an `outbound` job is due.

3. No business send can happen outside `actions/executor.py` (confinement test) or before a committed claim.
4. With the poller of **this process run** not caught up, or any inbound row pending, nothing is sent; a barrier left by a previous run never counts (R1).
5. `/pause` (command, stop word, fast lane) stops autonomous sending; its acknowledgement is sent after commit; `resume_autonomy` from a model never resumes without the owner's tap.
6. `/status` shows the actions block; logs content-free.
7. CP2: TL safety review signed off in `decisions.md` §D.

## 8. Risks

- **Race conditions** — mitigated by the protocol, the explicit-barrier tests (Antony re-runs them independently) and the state-machine test; CP2 blocks M04 integration until signed off.
- **Wrong recipient** — `BusinessTarget` resolution is account-scoped and keyed by the action's own conversation; a test sends in a two-account fixture and asserts the recorded `chat_id`.
- **Request timeout too long** — would let SIGTERM cut a send; fixed at 20 s with a test.
- **Dispatcher edits** for the after-commit acknowledgement touch an F0-owned file — keep the diff to the three branches.
