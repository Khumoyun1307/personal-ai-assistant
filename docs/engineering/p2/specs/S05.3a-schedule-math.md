## Goal

One small pure module that answers "when is the next occurrence?" for reminders, digests and scheduled summaries, correctly across daylight-saving changes and owner timezone changes. No database, no clock reads, no I/O: every function takes the time it needs as an argument.

## Design — the exact API

```python
TzPolicy = Literal["follow_owner", "fixed"]

class ScheduleError(ValueError):
    """An invalid schedule (bad rule, unknown timezone, wrong combination)."""

@dataclass(frozen=True, slots=True)
class ScheduleSpec:
    timezone: str                        # IANA name, e.g. "Europe/Berlin"
    tz_policy: TzPolicy
    rrule: str | None = None             # RFC 5545 RRULE body, no "RRULE:" prefix, no DTSTART/TZID inside
    dtstart_local: datetime | None = None  # naive LOCAL wall time of the first occurrence; required with rrule
    run_at: datetime | None = None       # aware UTC instant of a one-off; never with rrule

def validate(spec: ScheduleSpec) -> None                      # raises ScheduleError
def to_utc(local: datetime, timezone: str) -> datetime        # naive local wall time -> aware UTC
def next_occurrence(spec: ScheduleSpec, *, after: datetime) -> datetime | None
def rezone(spec: ScheduleSpec, new_timezone: str) -> ScheduleSpec
def daily_at(hhmm: str, timezone: str, *, starting: date) -> ScheduleSpec   # follow_owner, FREQ=DAILY
def next_local_time(hhmm: str, timezone: str, *, after: datetime) -> datetime

class Lateness(StrEnum): ON_TIME = "on_time"; LATE = "late"; SKIP = "skip"
def lateness(occurrence_at: datetime, now: datetime, *, grace: timedelta, max_lateness: timedelta) -> Lateness
```

Rules (each is tested below):
1. **`validate`**: exactly one of (`rrule` with `dtstart_local`) or `run_at`; `run_at` must be aware (any offset; it is compared as UTC); `dtstart_local` must be naive; `timezone` must load with `ZoneInfo`; the rule must parse with `dateutil.rrule.rrulestr(rule, dtstart=dtstart_local)`; `FREQ=SECONDLY` and `FREQ=MINUTELY` are rejected (too frequent); a rule containing `DTSTART` or `TZID` is rejected. Any failure → `ScheduleError` with a short reason (no user text echoed beyond the field name).
2. **`to_utc(local, timezone)`** — the single place local wall time becomes an instant:
   - **Ambiguous time (DST "fall back")**: use the **first** occurrence: `local.replace(tzinfo=zone, fold=0)`.
   - **Non-existent time (DST "spring forward" gap)**: detected when converting `local.replace(tzinfo=zone, fold=0)` to UTC and back gives a different wall time. Then return the **first valid instant after the gap**: the earliest UTC instant (to the second) whose local wall time is ≥ `local`. Find it by binary search between the `fold=1` and `fold=0` conversions of `local` (both are UTC instants on either side of the transition).
   - Return value: aware, `tzinfo=UTC`.
3. **`next_occurrence(spec, *, after)`**: `after` is aware. One-off: `run_at` (as UTC) if it is strictly after `after`, else `None`. Recurring: evaluate the rule on **naive local wall times** starting at `dtstart_local` (`dateutil.rrule.rrulestr`), convert each candidate with `to_utc`, and return the first one **strictly after** `after`. Start the search at `after` converted to local wall time minus one day (so a candidate shifted by a gap is not missed). Give up after 1 000 candidates (return `None`). A rule whose `COUNT`/`UNTIL` is exhausted → `None`. Because ambiguous times always map to `fold=0`, a daily 02:30 rule fires **once** on a fall-back day.
4. **`rezone(spec, new_timezone)`**: `follow_owner` → the same spec with `timezone = new_timezone` (same local wall times, new instants); `fixed` → the spec unchanged. A one-off (`run_at`) is always unchanged (relative reminders are stored as a UTC instant, ARCHITECTURE §12.4).
5. **`daily_at("21:00", tz, starting=d)`** → `ScheduleSpec(tz, "follow_owner", rrule="FREQ=DAILY", dtstart_local=datetime(d.year, d.month, d.day, 21, 0))`. `hhmm` must match `^([01][0-9]|2[0-3]):[0-5][0-9]$` else `ScheduleError`.
6. **`next_local_time(hhmm, tz, *, after)`**: the next instant strictly after `after` at which the local wall time is `hhmm` (today if still ahead, else tomorrow), via `to_utc`.
7. **`lateness`**: `now − occurrence_at ≤ grace` → `ON_TIME`; `≤ max_lateness` → `LATE` (fire with a note); otherwise `SKIP` (skip with a note, FR-FUP-08). Negative delays (early) are `ON_TIME`.

## Tests (red first) — `tests/unit/test_schedule.py`

Dates: 2026-03-29 and 2026-10-25 are the last Sundays of March and October 2026 (Europe/Berlin changes at 01:00 UTC on both). Asia/Tashkent is UTC+5 and Europe/Moscow UTC+3, neither with DST. `Z` = UTC.

- `test_to_utc_plain_time` — `to_utc(2026-11-02 09:00, "Europe/Berlin") == 2026-11-02T08:00Z`.
- `test_to_utc_in_the_spring_gap_gives_the_first_valid_instant` — `to_utc(2026-03-29 02:30, "Europe/Berlin") == 2026-03-29T01:00Z` (03:00 CEST).
- `test_to_utc_in_the_autumn_fold_gives_the_first_occurrence` — `to_utc(2026-10-25 02:30, "Europe/Berlin") == 2026-10-25T00:30Z`.
- `test_berlin_daily_0230_across_spring_forward` — spec `FREQ=DAILY`, `dtstart_local=2026-03-27 02:30`, Berlin, follow_owner: next after `2026-03-28T01:00Z` is `2026-03-28T01:30Z`; next after that is `2026-03-29T01:00Z`; next after that is `2026-03-30T00:30Z`.
- `test_berlin_daily_0230_runs_once_on_fall_back_day` — `dtstart_local=2026-10-23 02:30`: next after `2026-10-24T00:30Z` is `2026-10-25T00:30Z`; next after that is `2026-10-26T01:30Z` (never `2026-10-25T01:30Z`).
- `test_berlin_daily_0900_keeps_local_time_across_both_changes` — next occurrences around the changes: `2026-03-28T08:00Z`, `2026-03-29T07:00Z`; `2026-10-24T07:00Z`, `2026-10-25T08:00Z`.

- `test_tashkent_to_moscow_fixed_keeps_the_utc_instant` — the same spec with `tz_policy="fixed"`: after `rezone` the next occurrence is still `2026-11-01T16:00Z`.
- `test_a_relative_one_off_reminder_is_unchanged_by_a_timezone_change` — `run_at=2026-11-01T10:00Z`, follow_owner or fixed: `rezone` returns an equal spec and the next occurrence after `2026-10-31T00:00Z` is `2026-11-01T10:00Z`.
- `test_a_one_off_in_the_past_has_no_next_occurrence`.
- `test_leap_day_rule_skips_to_the_next_leap_year` — `FREQ=YEARLY;BYMONTH=2;BYMONTHDAY=29`, `dtstart_local=2024-02-29 09:00`, `"UTC"`: next after `2026-10-26T00:00Z` is `2028-02-29T09:00Z`.
