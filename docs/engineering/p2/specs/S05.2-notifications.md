## 1. Goal

One path for everything the assistant tells the owner unprompted: alerts are enqueued as content-free `notifications` rows, a pure policy decides immediate / deferred / batched / suppressed from urgency, contact priority, quiet hours, the hourly cap and the owner's feedback, and delivery is at most once. System alerts keep their exact current behaviour and are never delayed. The owner can set contact priority, and NFR-05 can be measured on the server.

## 2. Scope

**In:** `inbox/notification_policy.py` (pure); `inbox/notifications.py` (`enqueue`, delivery service, renderers registry); `inbox/alert_texts.py`; `notify.deliver` job; notifications reconciler; feedback and "Open chat" buttons (`ntf` callback kind, `telegram/control/alerts.py`); migration of every `OwnerAlerts.notify_owner`/`notify_all_owners` caller onto the notifications path (CP4); `conversations/priority.py` and the `set_contact_priority` tool (echo + Undo); `deploy/sql/nfr05.sql` + `deploy/server.sh nfr05`; `/status` notifications line; flag `notifications.deliver`.

**Out:** the settings UI (S05.2P builds it on F0's preference keys and this unit's `conversations/priority.py`); digest composition (S05.3b — it consumes `batched` rows); triage and monitor logic (S05.1, S05.4 — they call `enqueue`).

## 3. Design and implementation requirements

### 3.1 Policy (`inbox/notification_policy.py`, pure — no I/O, unit-tested exhaustively)

```python
class Verdict(StrEnum): IMMEDIATE = "immediate"; DEFER = "defer"; BATCH = "batch"; SUPPRESS = "suppress"
@dataclass(frozen=True, slots=True)
class NotificationFacts:  kind: NotificationKind; alert_class: AlertClass; priority: Priority
                          contact_id: int | None; contact_priority: str | None; bypass_quiet_hours: bool
@dataclass(frozen=True, slots=True)
class OwnerAlertSettings: timezone: str; quiet_hours: tuple[time, time] | None; urgent_bypass: bool
                          cap_per_hour: int; muted: frozenset[tuple[str, int | None]]   # (kind, contact_id)
@dataclass(frozen=True, slots=True)
class RecentLoad:         immediate_last_hour: int; suspicious_from_contact_24h: int
@dataclass(frozen=True, slots=True)
class DeliveryDecision:   verdict: Verdict; deliver_after: datetime | None; reason: str
def decide_delivery(facts, settings, load, now: datetime) -> DeliveryDecision
```
Rules, in order (each returns a decision with a reason code):
1. `alert_class == SYSTEM` → `IMMEDIATE` (`system`). Never deferred, batched, capped or suppressed (ARCHITECTURE §17).
2. **Effective priority:** contact `vip` raises one step (low→normal→high→urgent), `low` lowers one step (never below `low`) — **except `MONITOR_MATCH`, which is never lowered** (the owner asked for that monitor explicitly; R9); `TRIAGE_SUSPICIOUS` with `suspicious_from_contact_24h ≥ 1` (a repeat) is at least `high` (PRD §11.5 "alert if repeated").
3. The alert's exact pair `(kind, contact_id)` in `muted` (an alert naming no contact matches `(kind, None)`; that pair never mutes alerts that name a contact — P2-T38) and effective priority below `urgent` → `BATCH` (`feedback`).
4. Effective `low`/`normal` → `BATCH` (`quiet_by_default`, PRD §6.7).
5. Inside quiet hours (owner-local; a range may wrap midnight): effective `high` or `urgent` with `bypass_quiet_hours` (a monitor spec that asked for it, R9) → continue to rule 6; effective `urgent` with `urgent_bypass` → continue to rule 6; effective `high` otherwise → `BATCH` (`quiet_hours`; PRD §14 "quiet hours suppress non-urgent alerts into the next digest"); effective `urgent` otherwise → `DEFER` until the quiet hours' end, as a UTC instant (`quiet_hours`) — held, never dropped.
6. `immediate_last_hour ≥ cap_per_hour` → `BATCH` (`cap`) for every standard alert, urgent included (FR-TRI-07; only `system` is exempt, rule 1). Every `IMMEDIATE` standard alert counts toward the cap, including rows claimed `uncertain` (the claim state), so concurrent claims cannot exceed it (P2-T38).
7. Otherwise `IMMEDIATE`.

`muted` is **derived, not stored** (TL decision (spec), no new preference key): a `(kind, contact_id)` pair is muted when the owner marked ≥ 2 of its notifications `not_useful` in the last 30 days and none `useful` since the latest `not_useful`. It is computed from `notifications.feedback` (30-day retention fits).

### 3.2 Enqueue and delivery (`inbox/notifications.py`)

- `enqueue(...)` exactly as F0-interfaces §8.3: `INSERT … ON CONFLICT (account_id, dedupe_key) DO NOTHING RETURNING id`; when inserted, register an after-commit defer of `notify.deliver(notification_id)` (qlock `notify:{id}`). Returns `None` for a duplicate. Dedupe keys are ids and enums only.
- **Delivery service** `deliver(notification_id)`, run by the job:
  1. Short transaction: lock the account, then load the row (P2-T42: a `standard` row takes the account `FOR NO KEY UPDATE` from the load count to the claim, so two alerts cannot both take the last cap slot; a `system` row takes `FOR KEY SHARE`, which never waits on that lock — rule 1); never across the send; if `status != 'queued'` → done (idempotent). If flag `notifications.deliver` is off and the class is `standard` → leave it `queued` (it will be delivered or batched once on). Compute facts, settings (F0 preference accessors), load (counts from `notifications` in the last hour with `status = 'sent'` and class standard; suspicious count per contact), and decide.
  2. `BATCH` → `status = 'batched'`, `reason_code`. `SUPPRESS` → `status = 'suppressed'`. `DEFER` → set `deliver_after`, keep `queued`, register an after-commit defer at `deliver_after`. Commit. Done.
  3. `IMMEDIATE` → **claim**: `UPDATE notifications SET status = 'uncertain', reason_code = 'claimed' WHERE id = :id AND status = 'queued'` — the at-most-once claim (TL decision (spec): F0's status set has no `sending`; `uncertain` is the right fail-safe — a crash after the claim leaves the alert uncertain and it is never resent, ARCHITECTURE §17 / invariant 6 spirit). Render (§3.3) inside the transaction; commit.
  4. Send through the `ControlChannel` port (no transaction open).
  5. Record: ok → `sent`, `sent_at`, `message_id`; definite failure (`Delivery.ok` false, not uncertain) → back to `queued` with `reason_code = 'not_delivered'` and a bounded retry (≤ 3 attempts, then `failed`); uncertain → stays `uncertain` with `reason_code = 'ambiguous'`. These queued retries apply to standard notifications. The synchronous system path in §3.5 has terminal failed attempts and leaves retries to existing callers (CP4 ICR #132).
- **Rendering at delivery from ids (P2-T12):** a renderer per kind (`inbox/alert_texts.py::RENDERERS: dict[NotificationKind, Renderer]`, `Renderer = Callable[[AsyncSession, Notification, AccountView], Awaitable[RenderedAlert | None]]`). Renderers read the domain rows named by `refs` (contact display name, the latest triage verdict's reasons, task titles, the monitor's description) inside the delivery transaction and escape HTML. A renderer returning `None` (a referenced row is gone — e.g. the chat's data was deleted) → `suppressed`, `reason_code = 'source_deleted'`. S05.4 registers the `MONITOR_MATCH` renderer from its own module (via `_wire_m05`); S05.1's kinds are rendered here.
- **Buttons** (`ntf` kind, F0-interfaces §7): each standard alert that names a conversation is a card (`pending_inputs` kind `ntf`, `ref_id` = notification id, created in the claim transaction): "Open chat" (`op`), "Not useful" (`nu`), "Useful" (`us`). **TL decision (spec):** "Open chat" is a callback, not a URL button (the `ControlChannel` port has callback buttons only): the handler sends the conversation panel (`panels.panel_screen` / `handle_panel_command` path) for the referenced conversation after re-checking it is the presser's. Feedback presses set `notifications.feedback` (last press wins) and answer "Noted — fewer alerts like this" / "Noted"; the card's buttons stay so the owner can change the answer.

### 3.3 Owner-facing alert texts (`inbox/alert_texts.py`, English in P2 — P2-O11)

Each alert says what happened, why it matters (the rule) and what can be done next (PRD §14). Triage kinds: "<contact> needs a decision from you", "<contact>: urgent", "<contact> is waiting for a reply", "<contact>'s messages look like an attempt to instruct the assistant — I did not act on them" (suspicious), "Closed automatically: <task title> (<contact>)". Include the triage reasons as given (escaped). Never include message text itself (only reasons and titles the product already shows in summaries).

### 3.4 Job and reconciler

- `notify.deliver(notification_id)` on `outbound`, qlock `notify:{id}`, bounded retry on transient DB errors only, never after the send.
- Reconciler (`jobs/reconcile_inbox.py`): `queued` rows older than 30 s whose `deliver_after` is NULL or due, with no `todo`/`doing` `notify.deliver` for that id → defer. (With the flag off, standard rows stay queued; the reconciler skips them so it does not churn.)

### 3.5 System alerts onto the notifications path (CP4, after `int/m05` merges `main`)

This is the definition of the CP4 migration (R10): **callers do not change**; `notify_owner` routes through `notifications` internally. `OwnerAlerts.notify_owner` / `notify_all_owners` keep their **signatures, return values (`AlertResult`) and synchronous delivery** — callers (`agent/budget.py`, `inbox/watchdog.py`, `inbox/connection_alerts.py`, `inbox/policy_notice.py`, `inbox/backup_check.py`, `jobs/tasks.py`, and M04's `DELIVERY_UNCERTAIN`/`CONNECTION_STALE` callers) do not change. Inside, `notify_owner`:
1. Dedupe check **keeps reading the existing `system_alert` audit rows** (`audit_log`, 1-year retention), exactly as today — never `notifications`, whose rows are swept after 30 days and which starts empty at deploy, so a once-ever key such as `budget:{YYYY-MM}:{percent}` would otherwise be sent again (R10). The only change: an audit row recording an **uncertain** outcome now counts as sent (P2-T24, step 3). A failed (definitely not delivered) attempt does not count, as today.
2. The synchronous `inbox/system_notifications.py::SystemNotificationDelivery` helper takes account `FOR KEY SHARE`, then the system-key transaction advisory lock described below. Read unresolved claims and the historical outcome dedupe under that serialization. Insert `alert_class = 'system'`, `kind = SYSTEM`, `priority = 'urgent'`, `refs.alert_kind = kind`, `status = 'uncertain'`, `reason_code = 'claimed'`, and `dedupe_key = f"sys:{dedupe_key}:{attempt_ms}"`. Append `system_alert_claimed` audit details `{kind, key, notification_id, attempt_ms}` and commit **before** the channel call. Values, rendered text and buttons remain ephemeral; no queued job reconstructs or retries this attempt.
3. **TL decision (spec):** a system alert whose outcome is uncertain now counts as sent (never resent). This applies everywhere what `policy_notice` already does, and closes the M02 follow-up "once-ever alerts resend after an uncertain outcome". It is the only visible change; record it in the PR.
4. System alerts ignore `notifications.deliver`, quiet hours, the cap and feedback (rule 1).
5. After the channel call, append exactly one immutable `system_alert` resolution per claim, retaining legacy `{kind, key, delivered, uncertain?}` and adding `{claim_id, notification_id}`. The audit ID of the claim is `claim_id`. Update a surviving notification to `sent`, `uncertain/ambiguous` or terminal `failed/not_delivered`; a deleted notification does not prevent recording the resolution. A definite failure releases the claim for caller-owned retries; standard queued retries remain unchanged.
6. An unresolved claim returns additive `AlertResult(sent=False, reason='in_progress', uncertain=False)` and never expires merely because cooldown elapsed. This avoids settling a policy-notice marker before its actual outcome. Historical/completed success and uncertainty return `duplicate` under the existing cooldown. Dedupe joins are account-scoped and use the one-year audit history, surviving the notification sweep. No audit history is mutated.
7. Approved CP4 ICR #132: the two-int4 `pg_advisory_xact_lock` namespace is `0x53595341` (SYSA). Its signed key is the first four SHA-256 bytes of canonical UTF-8 JSON `[account_id, dedupe_key]` (compact separators, literal Unicode). Hash collisions only serialize briefly; exact account/key predicates determine dedupe. Order is account KEY SHARE → advisory → notification/audit; neither lock nor transaction crosses the send. Standard cap claims never use this namespace. Under serialization `attempt_ms = max(clock_epoch_ms, prior_claim_attempt_ms + 1)`, incrementing past an existing notification-key collision. Frozen/backward clocks therefore never reuse an attempt key. [PostgreSQL 18 advisory locks](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS).
Tests prove each caller's behaviour unchanged against its existing tests (they must stay green untouched, except the uncertain-resend case, whose test is updated to the new rule with the TL's sign-off).

### 3.6 Contact priority (`conversations/priority.py`, `agent/tools/priority.py`)

- `set_priority(session, *, account_id, contact_id, priority, actor, clock) -> PriorityChange` — validates `vip|normal|low`, account-scoped (`core/errors.py::NotInAccountError` for a foreign or unknown id), no-op when unchanged, writes audit `contact_priority_changed` (`details = {"contact_id", "old", "new"}`), returns the audit id. S05.2P's panel calls this.
- Tool `set_contact_priority` (F0-interfaces §9): class `configure`, flag `tool.set_contact_priority`, args `{contact_id: int, priority: Literal["vip","normal","low"]}` (strict), `returns_managed = False`, `describe` names the contact (escaped) for the confirmation card in tainted runs; idempotent on `(run_id, tool_call_id)` via the audit row; echoed with Undo through `agent/tools/echo.py::queue_echo`; `memory/undo.py` adds `contact_priority_changed` to `UNDOABLE_EVENTS` and reverses only while the value is still the one this change set (S03.3 rule). Result to the model: `{"status": "ok", "changed": bool, "echo": …}` — ids only.

### 3.9 NFR-05 measurement (`deploy/sql/nfr05.sql`, `deploy/server.sh nfr05 [DAYS]`; used by the M05 live checklist §1.10 as `just prod <ip> nfr05 1`)

Pattern: `deploy/sql/nfr04.sql` + the `nfr04` action in `deploy/server.sh` + `tests/integration/test_nfr04_query.py`. `require_data_volume`; one read-only statement run with `PGOPTIONS="-c default_transaction_read_only=on"`; `:days` as a psql variable (default 1, validated `^[1-9][0-9]{0,3}$` in `server.sh`, never spliced into the SQL); reads timestamps, ids, run types, kinds and statuses only — never a content column; prints seconds and counts:
- **Triage completion:** for `agent_runs` with `run_type = 'triage'` and `status = 'succeeded'` in the window, latency = `finished_at − messages.sent_at` of the message id parsed from `trigger_ref` (`split_part(trigger_ref, ':', 5)::bigint`); p50, p95, count. Target p95 < 90 s.
- **Urgent alert delivery:** `notifications` with `kind = 'triage_urgent'`, `status = 'sent'` in the window, latency = `sent_at − max(sent_at)` of the messages in `refs.message_ids`; p50, p95, count. Target p95 < 2 min.
- **Feedback** (PRD R2 #7, for the trial): immediate standard alerts sent in the window, and the share marked `not_useful`.
Tests (`tests/integration/test_nfr05_query.py`): `test_the_query_reads_no_content_column`, `test_the_query_is_one_read_only_statement`, `test_triage_latency_is_measured_from_the_newest_burst_message`, `test_urgent_alert_latency_uses_the_newest_referenced_message`, `test_rows_outside_the_window_are_ignored`.

- **Changing the system-alert path** can silence a safety alert. Mitigation: keep the public API and audit rows, prove every caller with its existing tests, and review with Neryn (send-path owner).
- **Alert fatigue** — batching by default, the cap and derived muting; PRD R2 #7 measures it during the trial.
